## What the probe is (Repo-verified)

`.github/workflows/uptime-probe.yml` runs `bun scripts/uptime-probe.ts` with no secret, no environment and `contents: read`. The script makes two requests and nothing else:

1. `GET /` must be 200, `text/html`, with `x-content-type-options`, `x-frame-options`, `referrer-policy`, `permissions-policy` at the values in `apps/web/public/_headers` and a non-empty `content-security-policy`.
2. `GET /api/uptime-probe-does-not-exist` with a generated `x-request-id` (`uptime-probe-<base36 time>`) must be the 404 error envelope with an `x-request-id` and the four fixed security headers of `apps/api/src/app.ts`. The envelope check is shared with the preview smoke (`scripts/api-envelope.ts`).

Each request has a 10 s limit and redirects are not followed (any 3xx fails). Every failure is one fixed message; the script never prints a body, a header value, an error text or the URL beyond its origin. Only the base URL's origin is accepted: https, or http for `127.0.0.1` (tests).

## Set it up

- Repository variable (not a secret): Settings, Secrets and variables, Actions, Variables, New repository variable. Name `PRODUCTION_URL`, value the bare https origin of the production Worker, no path or query. The value is created at the v1.0.0 cutover ([cutover runbook](cutover-runbook.md)); this document records no URL.
- A dispatched run may pass `base-url` instead; it wins over the variable.
- With neither set, the run fails with "Uptime probe has no base URL". This is deliberate (Repo-verified, tested): a silent green run before production exists would read as a healthy site. Set the variable in the same step that makes production live, or accept red scheduled runs until then.
- The schedule is inert until the default-branch switch (GitHub runs schedules only from the default branch). Until then dispatch by hand: Actions, Uptime probe, Run workflow (Unverified until run).
- A failed run is announced only by GitHub's normal workflow-failure notifications (same decision as the token check, [maintenance runbook](maintenance-runbook.md)); routing to the owner depends on their notification settings (Unverified). No pager exists.

## SLO

- Objective: 99.5 percent of probe runs in a calendar month pass, measured by this probe only.
- Why 99.5: one Worker with static assets, one owner, no on-call, no paid monitoring. It allows 216 minutes (3.6 hours) a month, enough for a bad deploy found and rolled back in business hours, strict enough that a day-long outage is a breach. Revisit after three months of data; this is a target, not a promise to anyone.
- Cadence: every 30 minutes at :07 and :37 (48 runs a day, about 1,440 a month, each under a minute). Chosen because 15 minutes doubles the runs for little gain at this SLO, and one probe failure is an event worth a human look anyway. The repository is public, so standard runners should not be billed (Unverified here).
- Accounting: a failed run is charged 30 minutes (the interval to the next run). Error budget: 216 / 30 = 7 failed runs a month; the 8th breaches the SLO.
- Resolution is coarse, and the number is honest only with these limits: an outage shorter than 30 minutes may be missed entirely, and one failed run can stand for anything from a few seconds to about 60 minutes of real downtime. GitHub can delay or skip scheduled runs under load and disables schedules in a repository with 60 days without activity (GitHub documentation, Unverified here); a missed run is not counted as up or down, so read the month's failure count together with the number of runs that happened.
- The probe sees the site from GitHub's network, not users' browsers, and checks reachability and headers, not the station search (that needs the visitor's Google key and location, which the probe never uses).

## Triage: failing run to the request id

1. Open the failed run. The log has the fixed message and, on failure, the line `x-request-id sent to the API route: uptime-probe-...`. That id is generated by the script, not taken from the network, and is the search key.
2. Read the message and pick the row.

| Message                                                                                                 | Meaning                                                      | First check                                                                                                                             |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| no base URL, or base URL must be a bare https origin                                                    | configuration                                                | the `PRODUCTION_URL` variable or the dispatch input                                                                                     |
| timed out, or could not connect                                                                         | Worker, DNS or TLS unreachable                               | open the site from a browser; Cloudflare's status page; Workers Metrics for the Worker (no log line is written if the Worker never ran) |
| got a redirect                                                                                          | a redirect rule or domain change sits in front of the Worker | the custom domain and redirect rules                                                                                                    |
| GET / did not return 200 / text/html / missing a security header                                        | static assets or `_headers` changed                          | the last production deploy run; a page request writes no Workers Logs line, so there is nothing to search                               |
| Unknown API route did not return 404 / the error envelope / no x-request-id / missing a security header | the Worker code or its routing changed                       | step 3                                                                                                                                  |

3. Workers Logs: in the Cloudflare dashboard open the Worker's Logs and filter on `requestId` equal to the printed id (the app echoes a client id that matches `^[A-Za-z0-9_-]{8,64}$` and logs it). A healthy request is one line with `path` `/api/*` and `status` 404. A `status` of 5xx, or a line with `event` `error` and an `errorName`, shows the app failed. No line at all means the request never reached the app: `invocation_logs` is off by design, so turn it on to diagnose such an outage ([observability](observability.md)). Search soon: Workers Logs keeps 3 to 7 days. The dashboard path is not recorded here (Unknown).
4. If the last deploy is the likely cause, roll back first and investigate after: [deploy runbook](deploy-runbook.md), section 7. Re-dispatch the probe to confirm recovery; a green dispatch is the observation that proves it.
5. Record the incident's failed-run count against the month's budget (7 failed runs).
