Existing journeys and domain terms additionally require source-backed parity evidence: read [feature parity](../product/feature-parity.md) and the [glossary](../product/glossary.md), which cite the legacy baseline `af903d7` source (for example its [index page](https://github.com/tashfiqul-islam/metro-station-finder/blob/af903d7a2c1bf08165cfcf4a00ca0c0d73eedead/src/pages/index.tsx)). For authorized UI work specify loading, empty, success, failure and recovery states plus keyboard/focus, labels, screen-reader feedback and responsive layout checks relevant to slice. Preserve geographic station selection versus provider walking-route distance as distinct concepts. Read [testing](testing.md) for behavior, [security](security.md) for location/permissions and [API](api.md) for provider interaction. `bun run smoke` runs Playwright Test against the built web app (Chromium locally; Chromium, Firefox, WebKit and a mobile viewport in CI) with an axe accessibility scan on every page and failure on page or console errors; it covers only the synthetic scaffold page and its loading, success and error states. Record manual evidence for anything it does not exercise (screen-reader output, responsive layout, the criteria listed below) and list unrun automation honestly. ## Accessibility target: WCAG 2.2 AA (METRO-41)

The target is WCAG 2.2 level AA. `bun run smoke` enforces what a browser test can; the rest stays manual. The axe tag and rule facts are Repo-verified against the installed axe-core 4.14.0 (tag names and rule ids read from `axe.getRules()`); the `toMatchAriaSnapshot` syntax is Context7-verified against Playwright 1.64.1 (2026-11-05). Success-criterion names and levels come from the WCAG 2.2 text as I know it and were not re-fetched from W3C (Unverified).

- Automatic (axe, `AXE_TAGS` in `e2e/fixtures.ts`): rules tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, plus `best-practice`. A tag filter replaces axe's default rule set; the 27 rules that are enabled by default but carry none of the five tags (for example `landmark-one-main`, `region`, `heading-order`) are all `best-practice`, so adding that tag keeps them (measured in axe-core 4.14.0 by diffing the enabled-by-default ids from `axe.getRules()` against `axe.getRules(tags)`). `wcag22aa` selects only `target-size` (2.5.8 Target Size (Minimum)), which axe leaves off by default; axe cannot judge every 2.5.8 exception (inline text, equivalent control, user-agent default), so a pass is not proof. A test with 16 px adjacent buttons fails if the tag list is dropped.
- Keyboard test (`e2e/keyboard.ts`, `expectTabReachesEveryControl`): Tab reaches every control (2.1.1 Keyboard), its focus indicator differs from its unfocused look and it matches `:focus-visible` (2.4.7 Focus Visible), nothing covers it and it is at least partly in view (2.4.11 Focus Not Obscured (Minimum); the check is stricter, five points in the visible part must hit the control), and the page does not cancel Tab and Shift+Tab leaves the last control (no keyboard trap). DOM order is only a sanity check, not a 2.4.3 Focus Order verdict. Links are included only where a runtime probe shows the browser Tabs to them (WebKit may not), so each browser is measured (hosted CI on Linux WebKit ran the links test, so it Tabs to links there; Windows WebKit does not). Measured browser difference: on Linux WebKit in CI run 41970661692 a control that fits the viewport was still out of view when measured immediately after Tab, so the helper re-measures for up to 2 s until the focused control is partly in view; the in-view rule stays strict and its failure message prints the geometry. The cause (asynchronous scroll) is inferred, not observed; the rerun on Linux passed.
- Acceptance status: the helper meets the keyboard acceptance (proven on pages with controls, and failing on hidden focus, an unchanged indicator, an overlay, a trap, a missed focusable element and positive `tabindex`). The product itself has zero interactive controls today, so the page test pins `expected: 0` and asserts Tab focuses nothing. When controls appear that pin fails with instructions: set `expected` to the new count and add ARIA snapshot and keyboard cases. Until then no real control has been exercised.
- ARIA snapshot (`toMatchAriaSnapshot`, inline, `/children: equal`): `main` in the success state (heading, paragraph, `status` named "Scaffold status") and in the error state (`alert`), covering 4.1.3 Status Messages through `role=alert`. The same template passes in all four projects, so there are no per-browser forks.
- Manual (record evidence, not automated): real screen-reader output and live-region timing, 1.4.10 Reflow and 1.4.4 Resize Text (320 px, 200 %), 2.4.11 against sticky or transient overlays in future UI, 2.5.7 Dragging Movements, 2.5.8 exceptions, 3.2.6 Consistent Help, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication (Minimum). 2.4.13 Focus Appearance is AAA and out of scope.

## Error handling (METRO-58)

- `apps/web/src/main.tsx` renders `StrictMode > ErrorBoundary > App` and passes `rootErrorOptions` to `createRoot`. StrictMode (development only) mounts each effect, cleans it up and mounts it again, so an effect without cleanup shows up as a duplicate request or listener. `main.test.tsx` proves it twice: the fetch effect runs twice with the first signal aborted, and `ErrorBoundary.render` runs twice (so StrictMode wraps the boundary, not only `App`).
- `ErrorBoundary` (`error-boundary.tsx`) is a small class component, not `react-error-boundary`: React has no hook for boundaries, and a dependency adds nothing for one fallback. It catches render, lifecycle and constructor errors of its subtree only; event handlers, async callbacks and effects that reject must set their own error state (as `App` does for the fetch).
- The fallback is a `main` with a `role="alert"` section named by its `h1` ("Something went wrong"), a plain-English hint and a "Try again" `button` (native, so Enter and Space work). All fallback copy lives in `errorCopy`. Try again re-renders the children; if they throw again the fallback returns and takes focus again. There is deliberately no retry cap (out of scope).
- Focus: the alert section (`tabIndex={-1}`) takes focus when it mounts, so keyboard users land on it. `focus.css` (linked from `index.html`, bundled by Vite, `style-src 'self'`) gives `[tabindex="-1"]:focus` a 3px `CanvasText` outline, because Chromium's default ring for script focus is 1px (measured: the e2e outline-width check failed at 1px without the file). Trade-off, unverified with a real screen reader: `role="alert"` already announces on insertion and the focus move may announce the section name and content again, so some assistive technology may read the fallback twice. Both are kept: the ticket requires `role="alert"`, and keyboard users need the focus move.
- Reporting rule for any boundary fallback and any log the app writes about a React error: never render or log the error message, stack or component stack, because they can contain coordinates or URLs ([security](security.md)). `report-error.ts` logs `<label>: <name>` where the label is `Render error` (caught and uncaught) or `Recoverable error`, and the name is one of the seven built-in JavaScript error names, else `Error`, and `NonError` for a thrown non-Error. The `onCaughtError`, `onUncaughtError` and `onRecoverableError` root callbacks (React 19, Context7-verified against react.dev `createRoot`) all use it.
- Debuggability trade-off: setting those root callbacks replaces React's default logging, so the original message, stack and component stack are NOT printed to the console for any error React reports at the root, in development too. A developer who needs them must reproduce under a debugger or temporarily widen the reporter locally; do not commit that. Whether the browser still shows the raw error for an uncaught error through another channel is Unverified and must not be relied on.
- Known gap (predates METRO-58, not fixed here): `App.tsx` renders `error.message` of a failed status request in its own `role="alert"` ("Scaffold status unavailable: ..."). The message comes from the app's own status client (for example "Status request failed with HTTP 500"), not from a thrown render error, and the scaffold sends no coordinates, but the rule above does not hold for it. Proposed follow-up wording for the rule once the product has location input: "No component renders or logs `error.message`, a stack or a URL from a caught error; show fixed copy keyed by error class, and keep details to the status code." Open a ticket before changing `App.tsx`.
- Browser-verified (Repo-verified, Chromium only, `bun run smoke` against the production build, `e2e/error-fallback.e2e.ts`): a real render error (the success render made to throw) shows the named alert, the alert has focus and a visible outline of at least 2px, axe (WCAG 2.2 AA tag list) reports no violations, Tab reaches the retry button, Enter retries and the fallback regains focus, and neither the page nor the console contains the thrown message. Firefox, WebKit and the mobile viewport run only in CI and were not run locally.
- Not verified: screen-reader output (and the double announcement above), focus after a successful retry (focus falls back to `body` because the button is removed), 1.4.10 Reflow and 1.4.4 Resize Text of the fallback, and the `main.tsx` double render and effect behaviour in a real browser dev server (smoke runs the production build, where StrictMode does nothing).
