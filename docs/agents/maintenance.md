Locked tool installs and hook visibility (METRO-45). `mise.lock` (tracked, with the `.mise/locks/` dependency-graph sidecar) records per-platform URL and sha256 for every tool in `mise.toml`, for `windows-x64` and `linux-x64` only (`settings.lockfile_platforms`; macOS is not supported and would need `mise lock --platform` plus a reviewed entry). `mise install --locked` resolves tools only from the lock and fails on a checksum mismatch or a tool missing from the lock; verified 2026-11-05 on this machine by corrupting a recorded pkl checksum (install failed with "Checksum mismatch") and by removing the pkl entry ("not in the lockfile"). The lock verifies downloads, not files already installed or restored from a cache. What "locked" means where: CI installs are locked because every workflow that uses `jdx/mise-action` sets workflow-level `MISE_LOCKED: "1"` (a test globs `.github/workflows/*.yml` and fails if one lacks it); the action also adds `--locked` itself when `mise.lock` exists (mise-action README, Web-verified 2026-11-05), so the env is explicit belt and braces. Local installs are locked only if the developer runs `mise install --locked` as documented. `bootstrap` never runs mise: it does not install or verify tools, it validates that `mise.toml` and `mise.lock` agree (and that the running Bun and Node match the pins). mise has no read-only "verify the lock" command (`mise ls` has no `--locked`; `mise install --dry-run` does not download), so no stronger local check is claimed. `mise.toml` deliberately does not set `locked = true`: that would also lock personal global tools (for example `latest` entries) on a maintainer machine, so a personal global config that pins `latest` must be bypassed locally with `MISE_GLOBAL_CONFIG_FILE` pointing at an empty file. Trust anchors differ per tool: `gitleaks` and `pkl` checksums come from mise's metadata service (`checksum_source = "mise-versions"`, from the release asset digests GitHub reports), `actionlint` and `zizmor` also carry `provenance = "github-attestations"`, `hk` records a sigstore signer (`sigstore-oidc` workflow identity), and `bun` and `node` record the checksums published with their releases; none of these is an independently signed statement for every tool. `hk` locks as `backend = "packslip:github.com/jdx/hk"` because that is what mise 2026.10.25, the version every workflow pins, resolves for the short name `hk` (Repo-verified: the lock was generated with that exact version); a different mise could resolve another backend, which `scripts/mise-lock.ts` would then report. `npm:renovate` records its resolved dependency graph (`aube` digest plus the tracked sidecar) and its `trust_policy_excludes` option, so the owner-approved `@yarnpkg/libzip@3.2.2` exception is part of the lock. Update a pin by editing `mise.toml`, running `mise lock` (never edit `mise.lock` by hand), reviewing `git diff mise.lock .mise` and committing both; `scripts/configuration.ts` (part of `check` and `bootstrap`) calls `scripts/mise-lock.ts`, which fails when the lock and `mise.toml` disagree on the set of tools, version, specifier, reviewed backend (a table in the script; add a new tool there in the same change), `trust_policy_excludes`, or when a platform entry lacks a sha256 checksum or an https `github.com`/`nodejs.org` URL containing the pinned version. For npm tools it checks that `aube.path` stays under `.mise/locks/` and that `aube.digest` equals the sha256 of the tracked `aube-lock.yaml` (reproduced against mise 2026.10.25). It does not re-download anything, so it cannot tell whether a recorded checksum matches the real artifact; mise does that at install time. `/mise.lock` and `/.mise/` are in CODEOWNERS. Renovate documents `mise.lock` updates and `lockFileMaintenance` (`mise lock --bump`) for the mise manager, which needs `mise` in self-hosted `allowedUnsafeExecutions`; whether the hosted Renovate used here runs it is Unverified. If it does not, a Renovate pin bump fails `check` visibly until `mise lock` is run on the PR branch. Sources (Web-verified 2026-11-05): https://mise.jdx.dev/dev-tools/mise-lock.html, https://mise.jdx.dev/configuration/settings.html, https://github.com/jdx/mise-action, https://docs.renovatebot.com/modules/manager/mise/. Lock generation was run on Windows only; the linux-x64 entries were resolved by `mise lock` from release metadata and attestations, and the first ubuntu-24.04 CI run is the real check (Unverified until then).

`bootstrap` also warns, without failing, when `pre-commit`, `commit-msg` or `pre-push` hk hooks are not configured in Git (`git config --get-regexp '^hook\.hk-.*\.event$'`, which sees per-repo and global installs) and prints `mise exec -- hk install --mise`. It warns instead of failing because a fresh CI checkout never has hooks and CI is the backstop; it is skipped when `CI=true` and outside a Git checkout. If Git cannot be run it prints a "could not determine" warning with the same command instead of crashing. The required hook names are tied to `hk.pkl` by a test. On Git older than 2.54 hk writes script shims, which this check does not see, so it warns anyway; upgrade Git. hk 2.11.0 has no status command (Repo-verified via `hk --help`).

## Cloudflare preview (METRO-13)

Same-repository pull requests get a Worker `metro-scaffold-pr-<number>` on workers.dev, deployed by the `preview` job of `.github/workflows/quality.yml` after `checks`, `build` and `security` pass (skipped for documentation-only pull requests, see [quality gates](quality-gates.md)); `preview-cleanup.yml` deletes it when the pull request closes. The job is outside the `Quality gates` aggregate. `CLOUDFLARE_API_TOKEN` (secret) and `CLOUDFLARE_ACCOUNT_ID` (variable) live only in the GitHub environment `preview`; a missing one fails the job with a message naming it. The token needs Workers Scripts edit for this account only; the owner rotates it (the first expiry, 2026-12-03, was extended by the owner to 2027-11-04; see the METRO-33 section below). Rollback: `wrangler rollback --name metro-scaffold-pr-<number>` returns the preview to its previous version (the job exercises it, then redeploys the checked commit). Never run these against `metro-scaffold` (production). Decisions: [specification](../specifications/cloudflare-preview.md), [ADR-0006](../adr/0006-cloudflare-preview.md).

## Release sync (METRO-14)

Publishing, editing, unpublishing or deleting a GitHub release runs `.github/workflows/release-sync.yml`, which keeps Plane aligned through `scripts/release-sync.ts`: the Plane release (looked up by tag name, never duplicated), its release tag (`git_tag`, `commit_hash`) and its release log (the GitHub notes rendered to HTML). GitHub is canonical. A stable release becomes `released` only when a successful `production` deployment exists for the tagged commit (none exists before METRO-11); a prerelease, draft or retracted release never does. Historical released Plane releases (`v0.0.1`, `v0.0.2`) are never modified. Publishing a release never changes work item states.

- **Run it by hand:** Actions, Release sync, Run workflow, tag `vX.Y.Z`. Use this after a failed run; the run is idempotent.
- **Credential:** `PLANE_API_KEY` is a secret in the GitHub environment `release`, which requires the owner's approval for every run and only accepts tags `v*` and the branches `main` and `feature/metro-rebuild`. The key acts as its owner in Plane and expires 2027-02-03; rotate it before then.
- **Release notes** list the METRO tickets and pull requests included and have a "Deferred" heading for unfinished tickets; the sync reports a missing heading in the Plane description.
- **Retraction:** delete or unpublish the GitHub release; the next run resets the Plane release to `unreleased`. Specification: [release-sync](../specifications/release-sync.md).
- **Not covered:** creating a GitHub release from Plane (separate ticket, needs a trigger that works before the default-branch switch).

## Cloudflare token rotation and expiry alarm (METRO-33)

Cloudflare has no first-party OIDC for wrangler, so preview (and later production) deploys depend on a long-lived `CLOUDFLARE_API_TOKEN`; rotating it on time is the control. Without it an expired token fails every preview deploy. **Current expiry: 2027-11-04** (confirmed by the owner in the Cloudflare dashboard on 2026-11-04, after extending the existing token's expiry instead of creating a new token; the first live run of the check below, on 2026-11-04, reported "Token is active and expires in 365 days (2027-11-04T17:59:59.000Z)", so the date is verified through Cloudflare's token-verify API). Extend or rotate before 2027-10-21 (the alarm below fails from 14 days out). Extending the existing token is an accepted alternative to the rotation steps below: after extending, run the check (step 3) and record the date (step 5).

**Alarm.** `.github/workflows/cloudflare-token-check.yml` (Actions, Cloudflare token check, Run workflow) runs `scripts/cloudflare-token-check.ts` in the `preview` environment. It calls Cloudflare's token-verify API and fails on HTTP 401/403, on a status other than `active`, and when the token expires within 14 days; it prints the days remaining, never the token. It also has a weekly schedule (Mondays 06:17 UTC) that is inert until the default-branch switch, because GitHub only runs schedules from the default branch; until then dispatch it by hand, at least weekly during the last 30 days before expiry. A token with no expiry date passes with a note; set an expiry when rotating. Endpoints (Cloudflare docs, read 2026-11-04): `GET /accounts/{account_id}/tokens/verify` for account-owned tokens, falling back to `GET /user/tokens/verify` for user-owned ones ([account](https://developers.cloudflare.com/api/resources/accounts/subresources/tokens/methods/verify/), [user](https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/)).

**Where a failure is announced (decided 2026-11-04: use GitHub's default).** No extra channel is configured. A failed run notifies through GitHub's normal workflow-failure notifications (the person who triggered it or last edited the schedule, per their notification settings), so keep failed-workflow notifications on for the owner's account (GitHub Settings, Notifications, Actions). Because the weekly schedule is inert until the default-branch switch, the primary control until then is a calendar reminder on 2027-10-05 (30 days before expiry) plus a manual dispatch of the check; do not assume anyone is paged. Revisit the channel when the default branch switches and the schedule starts running. Decided by the agent on the owner's delegation ("accept default, whatever is best").

**Owner steps (the agent cannot rotate the token).**

1. In the Cloudflare dashboard open the CURRENT working token and copy its permission set exactly (Workers Scripts, Edit is the documented minimum, but wrangler can need more, for example Account Settings read; Cloudflare's own CI guidance uses the "Edit Cloudflare Workers" template, [GitHub Actions](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/), read 2026-11-04). Create the new token (account API token preferred; user token works) with exactly that set, resources limited to the one Metro account (no other accounts; add zones only if the current token has them), an expiry about 90 days out, and no IP filtering unless GitHub-hosted runners are accounted for.
2. In GitHub, repository Settings, Environments, `preview`, replace the secret `CLOUDFLARE_API_TOKEN` with the new value. Do not put it in a repository secret, a variable, a file, an issue or a chat. Leave the variable `CLOUDFLARE_ACCOUNT_ID` unchanged.
3. Verify: run the Cloudflare token check workflow by hand and confirm it passes and reports about the expected days remaining. That proves the token is active, not that it has every permission wrangler needs. Then re-run the `preview` job of a same-repository pull request (it deploys, exercises `wrangler rollback`, and redeploys) and confirm it passes with the new secret. Do not rely on `wrangler deploy --dry-run` for this: Cloudflare documents it as compiling and checking the project "without actually uploading the Worker" ([wrangler commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/), read 2026-11-04), and the docs for the newer `cf deploy --dry-run` say it makes no API requests, so it never exercises the token. It is safe to run but is not a permission check (Unverified for wrangler 4.156.0 specifically whether it contacts the API).
4. Revoke the old token in the Cloudflare dashboard only after step 3 passes.
5. Record the new expiry: update the date in this section and in the METRO-13 paragraph above, and note the rotation in the ticket. Set a calendar reminder about 30 days before it (for the current expiry: 2027-10-05).

**Environment.** The `preview` environment has no protection rules, by owner decision ([evidence](../evidence/metro-cloudflare-preview.md)), so scheduled and manual runs use it as configured. Warning: if required reviewers are ever added to `preview`, this alarm would wait for approval and stop being an alarm, and so would every preview deploy; keep the alarm and the deploys on an environment without reviewers. The environment's deployment-branch policy has not been verified (the evidence records none set). Any branch allowed to use `preview` can read the token, the same exposure PR previews already have; keep the token scoped to the one account.

Accepted checks for this procedure are in `scripts/cloudflare-token-check.test.ts` and `scripts/cloudflare-token-check-workflow.test.ts`. The live workflow has not been run: it needs the workflow registered on the default branch (or dispatched from a branch the `preview` environment accepts) and the owner's go-ahead to use the real secret. Each verify request times out after 15 seconds.

## Wrangler types check on Windows

Wrangler 4.156.1 fixed `wrangler types --check` failing on CRLF checkouts (audit row RT-17). Installed when METRO-49 was decided: wrangler 4.156.0, which predates the fix; the newest published was 4.157.0. Bumping was out of scope there ([ADR-0014](../adr/0014-language-level-and-worker-types.md)).

Re-test after the next wrangler bump, on Windows, in a checkout with `core.autocrlf=true` (CRLF working files):

1. `mise exec -- bun run bootstrap`, then confirm `bunx wrangler --version` is at least 4.156.1.
2. `mise exec -- bun run --cwd apps/api types`, then `mise exec -- bun run types:check`. It must report the types as up to date. Re-checking out `apps/api/worker-configuration.d.ts` with CRLF endings (delete it and `git checkout` it) and running `types:check` again must still pass.
3. Commit the regenerated file if its runtime header changed. Record the result in the bump's ticket and delete this step if it passed.
