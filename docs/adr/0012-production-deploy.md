# ADR-0012: Production deploy with staged rollout, smoke and automatic rollback

- Status: Accepted (2026-11-05). The workflow exists but is inert until the owner completes the [deploy runbook](../agents/deploy-runbook.md); nothing in this ADR deploys anything.
- Ticket: METRO-57. Decisions were delegated by the owner ("decide and justify"). Related: [ADR-0006](0006-cloudflare-preview.md) (preview), [ADR-0007](0007-release-sync.md) (release sync), [ADR-0008](0008-default-branch-switch.md) and the [cutover runbook](../agents/cutover-runbook.md) step 4.1.

## Context

A stable release counts as shipped only when GitHub has a successful deployment of the tagged commit in the environment `production` ([release policy](../agents/release-policy.md)). `scripts/release-sync.ts` asks `GET /deployments?sha=<tag commit>&environment=production` and accepts any deployment of that SHA that has ever had a status `success` (Repo-verified, `hasProductionDeployment`). No production Worker, environment or workflow existed.

Research (Web-verified 2026-11-05 unless stated):

- `wrangler versions upload` uploads a version without deploying it; `--tag`, `--message`, `--var` exist. `wrangler versions deploy <id>@<pct>% ... --yes` makes a deployment that splits traffic; `wrangler rollback [version-id] --message ... ` replaces the deployment (a split included) with one version at 100 percent. Flags Repo-verified against the installed wrangler 4.156.0 `--help`. Sources: <https://developers.cloudflare.com/workers/wrangler/commands/workers/>, <https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/>.
- The first upload of a Worker must be `wrangler deploy`; `versions upload` fails on a Worker that does not exist (<https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/>).
- Only versions among the last 100 uploaded can be deployed or rolled back to (same page).
- Gradual deployments route each request independently by percentage. Static assets with content-hashed names then break: HTML from version A can request a file that only version B lacks, giving a 404. The documented cure is version affinity, a `Cloudflare-Workers-Version-Key` request header that the owner would have to set with a zone Transform Rule on the custom domain (<https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/version-affinity/>, <https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/>). The ticket said the interaction with assets was not confirmed. Result: assets are not unsupported, but a percentage split is only safe with an affinity rule that lives outside this repository and is not present. Our build emits hashed assets and routes `/assets/*` through the Worker so a missing file is a 404 (ADR-0011), which is exactly the failure the page describes.
- `Cloudflare-Workers-Version-Overrides: <worker>="<version-id>"` sends one request to a chosen version, even one at 0 percent, but only if that version is in the current deployment; a deployment serves at most two versions (<https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/>). Whether the override also selects that version's static asset set for `/` is Unverified; the smoke proves the Worker path (`/api/*`) through `x-preview-sha`.
- Version (preview) URLs follow `workers_dev` when `preview_urls` is unset, and ours is `false` for production (<https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/>). So production has no URL until the owner connects a custom domain.
- GitHub: a job that sets `environment:` waits for the environment's protection rules, gets the environment secrets only after approval, and GitHub creates a deployment for it; deployment branch and tag patterns are separate lists, wildcards do not match `/`; `prevent_self_review` exists (<https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments>). Policies are created with `POST /repos/{owner}/{repo}/environments/{name}/deployment-branch-policies` with `name` and `type` `branch` or `tag` (<https://docs.github.com/en/rest/deployments/branch-policies>). That a workflow naming a missing environment creates it unprotected on the first run is the owner's brief; this page set did not state it, so treat it as true and designed against (Unverified here).
- Cloudflare's CI guidance uses an account-scoped token from the "Edit Cloudflare Workers" template and warns against storing it in the repository (<https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/>). Whether a narrower custom token also works for `versions` and `deployments status` is Unverified.

## Decision

1. **Trigger and ref.** `.github/workflows/production-deploy.yml` runs on a pushed `v*` tag and on `workflow_dispatch`. The guard in `scripts/production.ts` allows only a stable tag `vX.Y.Z` and the branch `main` (the branch run is how the [cutover runbook](../agents/cutover-runbook.md) step 4.1 deploys the exact commit before the tag exists). Prerelease tags such as `v0.0.0-sync-test` and any other branch fail the guard before any secret is used; a prerelease never becomes `released` anyway.
2. **Approval.** Environment `production` with one required reviewer, the owner `tashfiqul-islam`, and deployment policies for tags `v*` and the branch `main`. `prevent_self_review` stays off: the owner is the only reviewer and also the person who pushes the tag, so turning it on would make every deploy impossible. No GitHub wait timer: the soak below sits inside the job where it can fail the run. `feature/metro-rebuild` is not in the policy (the ticket said "the protected branches"): the guard refuses it, a production deploy from the integration branch is never wanted, and the branch is retired at cutover step 6.3. The owner may add it; the guard would still refuse it.
3. **Rollout: stage at 0 percent, verify, then 100 percent. No intermediate percentage.** After upload the workflow deploys `previous@100% new@0%` (users see no change), smokes the new version on the production URL through a version-override header and proves with `x-preview-sha` that the response came from the new version and the released commit, then deploys `new@100%`, smokes the plain URL, waits `SOAK_SECONDS` (120) and smokes again. A 10/50 percent split was rejected for now because, without a version-affinity rule on the zone, it breaks pages for that share of visitors (see Context); it can be added as extra steps once the owner has configured affinity and the page-weight and traffic justify it. For the current traffic (none before v1.0.0) the 0 to 100 stage gives the realistic check (production hostname, bindings, headers, security headers) without a skew window.
4. **Automatic rollback.** Any failure after the previous version was recorded and staging was reached runs `wrangler rollback <previous-version-id>` and a smoke of the plain URL. The previous version comes from `wrangler deployments status --json`; a deployment that is already a split, or an unreadable shape, stops the run before anything changes (fail closed). The run stays red after a rollback so the `production` deployment status is `failure` and release-sync does not mark the release released.
5. **Same smoke as preview.** `smokePreview` is reused unchanged except for an optional `headers` option. A failed rollback smoke is visible in the run; a failed rollback itself leaves the run red with the previous version id in the summary for manual `wrangler rollback`.
6. **Deployment record.** The job-level `environment: production` creates the GitHub deployment for `github.sha`: for a tag push that is the tagged commit, which is what release-sync resolves from the tag. Its status is `success` only if every step passed. A second job `sync` (no environment, no secrets, `actions: write` only) then dispatches `release-sync.yml` for the tag, because a release is normally published before the tag deploy finishes and release-sync only reads current state. It needs its own `release` environment approval as before.
7. **Inert until enabled, fail closed.** The `deploy` job condition is `vars.PRODUCTION_DEPLOY_ENABLED == 'true'` (a repository variable the owner sets last). While it is unset the job is skipped, so the `production` environment is never referenced and cannot be auto-created unprotected. Cloudflare secrets exist only as environment secrets of `production`, never at repository level, so an auto-created environment would have none and the guard would stop the run. The order in the runbook is: environment with reviewer and policies, then secrets, then `PRODUCTION_URL`, then `PRODUCTION_DEPLOY_ENABLED`. The guard re-checks the variable in code.
8. **Custom-domain sequencing.** The workflow does not connect, change or require a domain change. `PRODUCTION_URL` (a repository variable holding the https origin) must exist and pass the guard, and the first production Worker must exist: the owner bootstraps it once with `wrangler deploy` (Context: first upload), then connects the custom domain under separate authorization, then sets the variables. Until then every run is skipped or fails at the guard or at `deployments status`, before upload.
9. **Credentials.** A dedicated production Cloudflare token as secret of environment `production` (not the preview token: the `preview` environment has no protection and runs code from pull requests), account scoped, built from the "Edit Cloudflare Workers" template or narrower after the owner verifies `versions upload`, `versions deploy`, `deployments status` and `rollback` work. The account id is an environment variable. The token is set only on steps that run Wrangler; the job restores no cache.
10. **Visible commit.** The upload passes `--var PREVIEW_SHA:<sha>`, so production API responses also carry `x-preview-sha`. The repository is public and the SHA is public; the header is how both smokes prove which commit runs. Renaming the header is a separate change. `--keep-vars` is not used: production has no dashboard variables (Unverified for the live Worker; the runbook asks the owner to check).

## Consequences

- Rollout is binary after a verified stage; a defect that only shows under real traffic reaches everyone at once, and the soak is 120 seconds, not hours. Rollback is one command and is automatic on a failed smoke only.
- A bad release found later is handled by `wrangler rollback` (runbook) or by fixing forward; release-sync does not un-release on its own.
- Live behaviour is Unverified until the owner's first run: the `deployments status --json` shape, whether `@0%` is accepted on this Wrangler, whether the override also selects the asset set for `/`, and the token permissions. Each failure path stops before traffic changes or rolls back.
- The ticket's live verification with a throwaway tag was excluded by the constraints of this change.
