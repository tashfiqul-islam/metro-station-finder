# ADR-0020: Budget the first visit, cap all files, and load features lazily

- Status: Accepted (the combined first-visit limit and the all-files ceiling are superseded by ADR-0023)
- Date: 2026-11-08
- Ticket and specification: METRO-104 (Plane); no separate specification, the ticket's owner decision of 2026-11-08 (gate policy, approved with "ok") is the contract.

> Partly superseded by [ADR-0023](0023-bundle-budget-model.md) (METRO-116, 2026-11-09): the first-visit limit is split into JS (250,000 / 80,000, unchanged) and CSS, and the all-files ceiling is replaced by per-screen limits and a shared lazy allowance, with unclassified chunks failing. Wherever the text below speaks of the ceiling, read ADR-0023. The first-visit set, the manifest rules and `lazyFeature` stand.

## Context

The bundle gate summed every JS and CSS file against 250,000 bytes raw and 80,000 gzip (METRO-12). After METRO-44 part B the build was 248,941 / 79,213, so the next feature of any size would fail, and a lazy chunk could not help because it counted the same as the entry. The budget exists to bound how much a first visit must download and parse, not how many files a product has. Part C added an entry-chunk check, then the orchestrator equalised it to the totals as an interim step ([ADR-0019](0019-telemetry-endpoint.md), [METRO-44c evidence](../evidence/metro-44c.md)), which left it inert.

- Context7-verified (Vite 8.3.5 docs): `build.manifest: true` writes `.vite/manifest.json` into the output directory. A chunk lists its static `imports` and its `dynamicImports` as manifest keys, and its `css` files. The HTML entry has key `index.html` and `isEntry: true`.
- Repo-verified: the client build writes `apps/web/dist/client/.vite/manifest.json`. `dist/client` holds `_headers`, `.assetsignore`, `favicon.svg`, `index.html`, `assets/index-*.css`, `assets/index-*.js`, `assets/web-vitals-*.js` and `.vite/manifest.json`; the plugin-written `.assetsignore` lists `wrangler.json` and `.dev.vars`, not `.vite`. The first dry-run counts (`wrangler deploy --dry-run` read 7 files before and 9 after, as a bare count) differ by exactly the two new build outputs, `assets/web-vitals-*.js` and `.vite/manifest.json`; with `WRANGLER_LOG=debug` the run lists each path. Left alone, the manifest would be uploaded and served at `/.vite/manifest.json`. It is a build artefact only `scripts/bundle-budget.ts` needs, and that script reads the local `dist/client`, not the deployed site, so `apps/web/public/.assetsignore` (`.vite`) now excludes it. The plugin merges that file into its own: the built `.assetsignore` lists `.vite`, `wrangler.json`, `.dev.vars`, and the dry-run logs `Ignoring asset: .vite` and `.vite\manifest.json` (Repo-verified).

## Decision

We will apply the existing limits, 250,000 raw and 80,000 gzip, to the first-visit set and add a separate ceiling for all emitted JS and CSS.

- First-visit set (`scripts/bundle-budget.ts`): the `index.html` manifest entry, the transitive closure of its `imports`, and the `css` of each, every file once. `dynamicImports` are never followed, so a lazy chunk and its CSS stay out. Gzip is computed per file, as before. Neither limit is raised.
- Ceiling for all files: 400,000 raw and 125,000 gzip, the owner's recommendation. After this change all files measure 250,801 / 80,244; the ceiling is about 1.6 times that, room for a few lazy features while a runaway still fails. It is a growth tripwire, not a load budget. All files already use about 63 percent of it, so it has little room; do not raise it to pass. The revisit rule is this prose plus a printed note: `bundle:check` prints the percent of the ceiling used and, above 50 percent, a non-failing "growth tripwire: revisit the ceiling" line. Nothing else enforces the revisit.
- `bun run bundle:check` lists every file marked `first-visit` or `lazy`, then prints both totals with their limits. It fails closed, with one fixed message, when the manifest is missing, unparsable, has no `index.html` entry, names an import the manifest lacks, or names a first-visit file that is not on disk. With a second fixed message it also fails when an emitted `.js` or `.css` file is not listed in the manifest (as a chunk `file` or in a `css` list), so an orphan or a stale manifest cannot pass. `.vite` is never counted in the sums. An import cycle terminates through a visited set. The interim entry check is removed; the first-visit check subsumes it.
- Pattern: a feature beyond the landing route is loaded with `lazyFeature(() => import("./features/x/X"))` from `apps/web/src/lazy-feature.tsx`: `React.lazy` inside `Suspense`, a fixed pending status (`<output>`, visible text, no spinner and no animation, so nothing depends on reduced-motion handling), and a fixed failure message with a "Reload the page" button (a native button calling an injectable reload, `window.location.reload` by default). It reloads rather than importing again because React caches a rejected `lazy` result, a browser may cache a failed `import()` of the same specifier for the life of the document (Unverified in a real browser), and after a deploy an old page asks for hashed chunks that no longer exist; only a reload fetches the new HTML and chunk names. On failure focus moves to a `tabIndex={-1}` region named by the fixed text, with no `role="alert"`, so the text is announced once, as on a route change. The error is never rendered; the root callbacks log only its built-in class name. Dynamic imports must be literal `import()` calls so Vite can split them.
- First use: `web-vitals` is loaded with `import()` once the page has loaded and is idle (`requestIdleCallback` with a 1 s timeout; a 1 s timer where it is missing). A failed load is dropped with no log, and each observer is registered in its own `try`, so one failing observer does not skip the others. The landing nearest-station feature stays in the entry chunk and no screen is added.

## Consequences

- Easier: a feature can be added without touching the limits as long as it is a lazy chunk; the first-visit figure then does not move. The first visit gained 7,161 raw and 2,814 gzip bytes of headroom.
- Harder: the gate depends on the Vite manifest format and on `index.html` being the entry key. A custom build input or a manifest key change fails closed and needs a script change.
- The vitals chunk costs more in total than it saved from the entry: the first-visit set fell 6,102 raw / 2,027 gzip while the chunk is 7,962 / 3,058 (separate-chunk and import-helper overhead). Less than the ticket's estimate of about 10 KB; the numbers are in [METRO-104 evidence](../evidence/metro-104.md).
- Residual bias, size Unverified: registration waits for load, then up to 1 s of idle, then the chunk fetch. A session hidden before that sends nothing for that page view, and background tabs throttle timers, so quick bounces are under-counted and the data skews toward longer visits. Real-user metrics now register after idle. The observers read buffered entries, so LCP and CLS history is kept, but an input that happens before registration cannot finalise LCP early; LCP is then sent when the page is hidden. The vitals e2e now waits for the chunk before its simulated hide, because a page already hidden when the library starts drops earlier entries.
- Unverified: the effect of the late chunk on real users' reported LCP, INP and CLS; the lab check cannot show it. Browsers without `requestIdleCallback` use the timer, not measured here. The real-browser failure and recovery path of the lazy helper (cached failed imports, a stale page after a deploy) is not exercised by a browser test; the unit tests mock the loader and the reload.
- Known minor: the pending `<output>` can flash on a fast load; accepted rather than adding a show delay.
- Preload gap: Vite's preload helper loads a dynamic chunk's dependencies only when the dynamic import runs, so the first-visit set equals the first page load for the current build. A future build with a service worker, a second `isEntry` file (it counted toward the ceiling only; under ADR-0023 it would be unclassified and fail the gate) or extra preload links would need the first-visit rule revisited.
- `modulePreload` interplay: Vite adds a preload helper to the entry for dynamic imports. This change keeps the default (`build.modulePreload` on); turning it off saved about 0.5 KB in ADR-0019's measurement on an earlier build, but also drops preloading for future lazy routes.

## Alternatives considered

- Raise the totals: rejected by the owner; it hides growth and does not bound the first visit.
- Sum a directory such as `assets/` as the first visit: rejected, it counts lazy chunks and penalises code splitting, which is the opposite of the goal.
- Parse `index.html` for scripts and preload links: rejected, it misses static chunk imports and CSS of imported chunks; the manifest is the build's own record.
- Keep a tighter entry-only budget beside the first-visit check: rejected, the entry is a subset of the first-visit set, so it adds a second number without protecting more.
- Static import of `web-vitals` (ADR-0019's choice under the old gate): superseded, the old gate could not reward splitting.
