# ADR-0018: Where the domain core runs

- Status: Accepted (the owner confirmed three answers directly on 2026-11-06, recorded in the Plane comment on METRO-84: no ticketing or payments ever, the two-date fare line, and no offline in v1 with the door kept open; the owner otherwise asked the agent to take the best decisions, and has not read this full text; the layering rule edit lands only through follow-up 1 with its own ticket and the owner's explicit scope)
- Date: 2026-11-06
- Ticket and specification: METRO-84 (Plane); no separate specification, the ticket acceptance is the contract. Evidence: [METRO-84 evidence](../evidence/metro-84.md). The number 0010 is unused in the repository history; this ADR takes the next free number, 0018.

## Context

Today `apps/web` may import only types from `@metro/core`: dependency-cruiser rule `web-never-imports-core-runtime` in `.dependency-cruiser.mts` forbids any runtime edge. [ADR-0009](0009-maps-provider-design.md) assumes the opposite for the first map slice: "the nearest station is chosen in the browser from our own dataset", the position "is not sent to our server", and fares and station lists "work with no map script loaded". The rule and the accepted ADR-0009 cannot both hold for the nearest-station slice, and the first reference slice decides what every later slice copies.

What the rule rests on. The sentence "the browser app gets every runtime value through contracts" is the comment on that rule (`.dependency-cruiser.mts`, lines 39 to 41, which cites ADR-0003); it is not a sentence of [ADR-0003](0003-contracts.md). ADR-0003 itself records a deliberate move: the status "moved from the page importing core directly to a Worker response the page must trust only after validation" (Context), and "the web app therefore imports no API code at all" (Decision). That move is about data crossing the wire: a response can be wrong or hostile, so the page validates it. It stays true and stays in force.

Facts, labels and sources are in the [evidence](../evidence/metro-84.md):

- Repo-verified: core is pure, dependency-free and tiny (16 stations, 16x16 fares, `baseline-v2`); the API has one scaffold route; the SPA and the Worker deploy atomically from one commit, so both always carry the same dataset bytes.
- Repo-verified, measured: the whole core public surface plus the dataset adds +4,874 bytes raw, +2,049 gzip (level 9), +2,050 gzip (default level, the one `bundle:check` uses) and +1,728 brotli (q11) to the web bundle (nearest, fare and dataset alone: +3,992 raw, +1,724 gzip level 9, +1,429 brotli). With the whole core in, `bundle:check` reports 230,751 raw and 72,471 gzip (default level) against the 250,000 and 80,000 budget, leaving 7,529 gzip bytes.
- Web-verified 2026-11-06: Workers Free allows 100,000 requests per day; static asset requests are free; requests matching `run_worker_first` (here `/api/*` and `/assets/*`) are billed Worker requests. Real traffic is Unknown, so no option is rejected on request counts (see the evidence model).
- Web-verified 2026-11-06: Google says browser keys use HTTP-referrer restrictions and server keys IP restrictions. That the Worker has no stable egress address is Inferred, not Web-verified (carried from ADR-0009). Whether `Route.computeRoutes` accepts a referrer-restricted key is Unverified.
- Web-verified 2026-11-06: a service worker can precache the app shell, with an update and versioning problem (`skipWaiting` can serve old pages with a new worker). No service worker ships today, so offline is only a possibility that this decision keeps open.
- Owner answers (2026-11-05, [nearest-station](../specifications/nearest-station.md) H1 to H3, [glossary](../product/glossary.md)): fares are Government fares, effective since launch; English only for now; the UI must not allow the same station at both ends.
- Fare provenance (R7), Repo-verified in [dhaka-mrt-line-6](../evidence/dhaka-mrt-line-6.md) (Primary, S2 and S3): the publisher that operates the service and hosts the fare table is Dhaka Mass Transit Company Limited (DMTCL); the fare authority is the Dhaka Transport Coordination Authority (DTCA), by a notice dated 2022-09-08, memo no. ৩৫.০২.০০০০.০১৬.৪৭.০০১.১৯-৩৭১. The notice states no separate effective date; fares were first charged when service opened on 2022-12-28. Web-verified 2026-11-06 ([Financial Express, 2022-09-09](https://today.thefinancialexpress.com.bd/print/metro-rail-fare-chart-published-1662659115), fetched by me): the DTCA published the chart on 2022-09-08, the article states no effective date and mentions only a planned December 2022 launch. The coordinator reports further secondary confirmation (Prothom Alo, Somoy News, the minister's announcement of 2022-09-06) that I did not re-fetch. No formal effective date was found anywhere (Unverified as a negative). So R7 is answered by recorded facts and needs no owner input; the effective-date field stays optional.

### Options

- **A: all computation in the API Worker** (status quo layering). Strongest honest case: one copy of the data and the rules, no layering change, no dependency edit, ADR-0003 holds literally, a fare table changing on a date changes for everyone at the instant of deployment (no stale tab shows the old fare once it calls the API), requests can be logged for analytics. (A ticketing flow would also have been served by it, but the owner has ruled ticketing and payments out.) Requests are not the problem it is sometimes made out to be: one bulk call for the station list and cacheable GETs for fares keep it to about 2 asset requests plus a few calls per session. Weakness: the rider's position must reach our server for nearest (the ADR-0009 consent copy would have to change), every lookup needs the network and a loading and failure state, and a Worker route plus contract exists for work a phone computes in microseconds.
- **A-prime: nearest station in the browser (what ADR-0009 requires), fare lookup and everything else through the API.** Strongest honest case: the position never leaves the device, and the fare, the one legally authored number, still has a server authority; a Government table that changes on a date for everyone at once changes at the deployment instant; a long-lived tab or a stale service worker cannot keep showing an old fare because the number is fetched; fare queries can be counted; the fare data leaves the bundle (measured: nearest plus stations only is +1,482 bytes raw and +853 gzip, against +3,992 raw and +1,724 gzip level 9 with fares, so fares and `findFare` cost 2,510 bytes raw and 871 gzip; the 16x16 matrix as JSON is 787 bytes raw, 156 gzip alone). Weaknesses: it needs the same layering change as B, which makes layering a non-differentiator between them (it is neither a reason for B nor for A-prime); it adds a contract, a Hono route, the ADR-0013 envelope path and a loading and error state for the fare page; the fare page needs the network (and dies with the Worker at its limit); and one dataset is split across two paths, so a stale tab and the server can disagree about the station set. Station ids are permanent and never reused (nearest-station specification), so the server forgetting an id a tab holds is unlikely (Inferred); the realistic skew is a stale tab lacking a newly opened station, and B has the mirror problem: a stale tab holds a fare table the deployed API has since changed.
- **B: core also runs in the browser; the API keeps what needs a server.** Nearest, search and fare in the browser from the dataset in the bundle; the API for the envelope, headers, observability and any future keyed or authoritative feature.
- **C: both; the API is the validating authority, the browser the fast path.** Strongest honest case: it combines B's speed with a server check. The check is not nearest-only: the server can validate a fare from two station ids with no position at all, and the check is deterministic (`findFare` is integer table indexing, so there is no floating-point drift). The weakness is purpose: the browser and the Worker run the same bytes of the same function, so the check can differ only under version skew, and then it only says "the newer deployment wins", which is A-prime's behaviour for fares at the price of a second request, a disagreement state and a second test surface.

## Decision

We will run `@metro/core` in the browser for station search, the nearest-station rule and fare lookup (option B), and will not add API routes that repeat those computations. This is accepted by delegation: the owner asked the agent to take the best decisions on 2026-11-06.

- The dataset ships inside the web bundle as part of core, reached through core's public entry only. `apps/api` keeps what needs a server (the error envelope and security headers, observability, and any later feature that needs a secret, shared state or an authority we do not have) and stays free to import core.
- Layering: only the rule changes. `web-never-imports-core-runtime` and its comment are replaced by `web-imports-core-public-entry-only` (exact edit under "Repository changes"). ADR-0003 is not edited and contains no sentence to amend. What stays true from ADR-0003: contracts govern everything that crosses the wire; web imports no API code; the page validates every API response with Valibot. Reversing the rule for pure local computation is acceptable now because there is no wire boundary and nothing to validate: a function call on the dataset in the same bundle cannot return a hostile or malformed body, and the code and the data are the same bytes the page was built from.
- Maps, Places and Routes stay in the browser with the referrer-restricted keys of ADR-0009. If Routes rejects a browser key or abuse appears, ADR-0009's Worker-proxy trigger adds an API route; the domain stays where it is.
- Authority. The authority behind the fares is the Government notice, not the client or the server; the dataset in the deployed bundle is the app's single versioned copy of it. A client never asks the server to confirm a fare today. The page shows one short English line with both dates, owner-confirmed on 2026-11-06 as "both dates": the date of the DTCA notice the fares follow and the date the table was last checked, for example "Fares: DTCA notice 8 Sep 2022. Checked 5 Nov 2026." (the two dates are data from the dataset; the example shows today's values). Follow-up 2 adds the fields.
- Offline is deferred. This decision does not deliver offline and does not rely on it: no service worker ships, and the decision is justified without it (below). It only avoids closing the door.
- Provenance (R7) is recorded, not open: publisher DMTCL, authority DTCA, notice 2022-09-08 with its memo number, first service 2022-12-28, effective date not stated in the notice. Follow-up 2 starts the dataset fields with these values; the effective-date field is optional.

### Reasoning

Why B beats A: A needs the rider's position on our server for the first slice, which contradicts the accepted ADR-0009 consent copy and would amend it; it adds a network round trip and failure state to a lookup the phone does instantly; and it keeps the repository's own decisions in conflict. A's remaining advantage (no layering change) is a one-rule edit.

Why B beats A-prime, shown and not asserted. A-prime's strongest case is a server authority for fares: instant change for all on a date, no stale tab, fare analytics. The owner's 2026-11-06 answer that ticketing and payments will never exist removes the transaction case: the app is information-only, so the server-authority case for A, A-prime and C rests only on dated fare changes and stale tabs, not on transactions. That answer strengthens B; it does not change the A-prime analysis below, it removes the argument that would have outweighed it.

(a) Layering is a non-differentiator: both need the identical rule edit, so it is not a reason for B.

(b) What the contrary data says about the fare table, from [dhaka-mrt-line-6](../evidence/dhaka-mrt-line-6.md) (Secondary except where stated). Changes that would alter the table (the 256 numbers) or the station set: the 2024 NBR letter that 15% VAT is payable (Tk 20 to 100 would become Tk 23 to 115), which did not take effect: DMTCL did not raise fares and exemptions were extended in rounds from 2022 to 2025, so the table stayed as published on 2022-09-08 (no revision found; Unverified as a negative); the Agargaon to Motijheel opening on 2023-11-04 (a station-set change); and the Kamalapur extension, expected about July 2027 (Secondary, no announced date), which makes the table 17x17 (the official table already has those numbers). Changes that are concessions applied at the gate and are not modelled in the dataset: the 10% smart-card discount and the free trips for war-wounded freedom fighters (2022 notice, Primary); the 2023 guideline; the separate special-need fare table; and the 25% concession for people aged 65 and over and persons with disabilities effective 2026-05-25. None of these concessions changes the standard single-journey fare the dataset holds; they are a product question (should the app show them) rather than a stale-tab question. For stale tabs the observed record is therefore: standard table changed 0 times in about four years, the station set changed once (2023) with one more expected, concessions changed in 2023 and 2026 outside the dataset. That is the base rate for "a long-lived tab shows a wrong fare"; it is low, not zero, and the VAT episode shows a number change can be announced at short notice.

(c) Honest cost summary: A-prime costs more now (a route, a contract, the envelope path, a loading and error state, a network dependency on the fare page), and saves 2,510 bytes raw and 871 gzip in the bundle. B costs a stale-tab mitigation later (follow-up 5), which is counted as B's cost, plus the visible dataset date. Moving B to A-prime later is a bounded change (a route, a contract and a call).

(d) The skew weakness of A-prime (a tab and the server disagreeing about the station set) is Inferred, and B has the mirror problem (a stale tab holds a fare table the server has since changed); the two are symmetric except that B's is rare and visible with a dataset date, while A-prime pays its costs every time.

(e) The sizes are measured (evidence section 2): the A-prime delta and the matrix figures above are from the existing probe approach, not estimated.

(f) The assumption on which the rejections of A, A-prime and C hang (no ticketing, payment or fare-dispute flow) is now owner-confirmed: on 2026-11-06 the owner said ticketing and payments will never exist ("NEVER EVER IN LIFE TIME, NOT POSSIBLE EVEN", recorded in the Plane comment on METRO-84). The app is information-only. The case for a server fare authority therefore rests only on dated fare changes and stale tabs, whose observed base rate is in (b).

The evidence still supports B over A-prime under that assumption, but the margin is cost now against a rare, mitigable staleness later, not a decisive technical difference.

Why B beats C: C's fare validation is real and deterministic, not nearest-only. It is rejected for now because it has no consumer: a check against the same bytes can differ only under version skew, nothing downstream (no payment, no dispute record) acts on the result, and it costs a request, a disagreement state and a second test surface per lookup. With ticketing ruled out by the owner, only a dated-fare-change problem could justify C or A-prime later.

## Consequences

- Easier: a nearest-station and fare result needs no network and no Worker request; the first reference slice has two layers (UI and core) and a golden path with no mandatory API step; the ADR-0009 consent copy stays true; Worker requests are spent only on assets and genuine server work; the decision is justified without offline, which stays possible.
- Harder: a fare correction needs a deploy and reaches an already open tab only on reload, so the dataset date must be visible and a stale-tab check is worth building (follow-up 5); the domain now runs in the browser engines riders use, so tests must prove it there; `apps/api` has little to do until a feature needs a server.
- Keeping the offline door open (owner answer: not in v1, possible after release). Choices that must not block a later service worker: keep hashed, immutable `/assets/*` files (ADR-0011) so a precache manifest can list them; keep the HTML shell and a future root `sw.js` on the default revalidating `Cache-Control` (never `immutable`) and keep the root path free for `sw.js`; no cookie or server-session dependence for any station, nearest or fare function (the domain needs no request at all); keep all domain data in the bundle rather than fetched at runtime (this decision); keep the dataset versioned with visible dates; no inline scripts or styles (the CSP, ADR-0011); no cache-busting query strings on assets; navigation by the SPA fallback only. No service worker, manifest or plugin is added now.
- Until follow-up 1 lands, the enforced rule `web-never-imports-core-runtime` and `docs/agents/architecture.md` still say web imports no runtime value from core. This ADR does not change either; changing a gate rule needs its own ticket and the owner's explicit scope, so the decision is Accepted but not yet in force in the repository.
- Not changed: at the Workers Free daily limit a cold load fails in every option, because the hashed assets are `run_worker_first` Worker requests (1027 or 429, Unverified which). A page already loaded keeps working. B does not fix that; ADR-0011 owns that cost and its trigger.
- Risks: nobody can check a fare against a server (accepted; the version is visible); cross-engine floating-point differences in Haversine could change a near-tie in nearest selection (Unverified; follow-up 4 tests Chromium, Firefox and WebKit); a service worker, if added, needs an update and kill-switch plan (Unverified in practice).
- Revisit triggers (any one reopens this ADR through a new one): a second consumer of the domain (a native app, a third party, shared links) that cannot run core; the web bundle running low on budget or the dataset growing (thresholds below); the standard fare table or the station set changing often enough that stale tabs show wrong fares (the observed base rate is in the A-prime reasoning); key abuse or Routes rejecting a browser key (then the proxy route appears; the domain stays); a measured disagreement of nearest selection between browsers; riders losing connectivity and the owner wanting offline after release (offline spike). Ticketing and payments are not a trigger: the owner ruled them out on 2026-11-06.
- Thresholds, provisional and justified from measurements. The first draft used "headroom below 20% of either budget"; that was already tripped before core (80,000 - 70,421 = 9,579 bytes = 12.0% of the gzip budget) and 9.4% after (7,529 of 80,000), so it could not work as a trigger and is replaced here, not silently loosened. Replacement: reopen when `bundle:check` gzip (default level) headroom falls below 5,000 bytes. Reason: the whole core public surface costs 2,050 bytes, so 5,000 is room for about two more additions of that size; the first UI slice is not yet measured, so the number is provisional and follow-up 3 must record headroom after the slice and recalibrate it. Dataset: reopen when the data portion exceeds about 5,000 bytes gzip. Reason: the matrix costs about 3.1 bytes raw per cell (787 bytes for 256 cells), so a network of about 40 stations (1,600 cells, roughly 4.9 KB raw before compression, Inferred linear) is where data starts to compete with the headroom; Kamalapur (17 stations, +33 cells) and even one more line of similar size are far below that. Also provisional.
- Reversibility: high (a wiring change) while no service worker exists; medium after, because a kill-switch worker is needed to remove one.

## Alternatives considered

- A, all computation in the API: rejected; reasons under "Why B beats A". It stays valid if a trigger fires.
- A-prime, nearest in the browser and fares through the API: rejected for now; reasons under "Why B beats A-prime". It is the first upgrade if fares start changing on dated schedules often enough that stale tabs cause wrong fares, which follow-up 5 would first try to prevent.
- C, both with the API as validating authority: rejected for now; reasons under "Why B beats C".
- B plus a service worker now: deferred; the offline value is not yet requested, and update behaviour, kill switch, Worker-first asset requests and plugin compatibility with the Cloudflare Vite plugin are unverified.
- Move Maps calls to a Worker proxy now: out of scope; ADR-0009 owns that decision and its trigger.
