# ADR-0018: Where the domain core runs

- Status: Accepted (by delegation: the owner asked the agent to take the best decisions, 2026-11-06; offline, ticketing and the fare publisher facts stay open as stated below)
- Date: 2026-11-06
- Ticket and specification: METRO-84 (Plane); no separate specification, the ticket acceptance is the contract. Evidence: [METRO-84 evidence](../evidence/metro-84.md). The number 0010 is unused in the repository history; this ADR takes the next free number, 0018.

## Context

Today `apps/web` may import only types from `@metro/core`: dependency-cruiser rule `web-never-imports-core-runtime` in `.dependency-cruiser.mts` forbids any runtime edge. [ADR-0009](0009-maps-provider-design.md) assumes the opposite for the first map slice: "the nearest station is chosen in the browser from our own dataset", the position "is not sent to our server", and fares and station lists "work with no map script loaded". The rule and the accepted ADR-0009 cannot both hold for the nearest-station slice, and the first reference slice decides what every later slice copies.

What the rule rests on. The sentence "the browser app gets every runtime value through contracts" is the comment on that rule (`.dependency-cruiser.mts`, lines 39 to 41, which cites ADR-0003); it is not a sentence of [ADR-0003](0003-contracts.md). ADR-0003 itself records a deliberate move: the status "moved from the page importing core directly to a Worker response the page must trust only after validation" (Context), and "the web app therefore imports no API code at all" (Decision). That move is about data crossing the wire: a response can be wrong or hostile, so the page validates it. It stays true and stays in force.

Facts, labels and sources are in the [evidence](../evidence/metro-84.md):

- Repo-verified: core is pure, dependency-free and tiny (16 stations, 16x16 fares, `baseline-v2`); the API has one scaffold route; the SPA and the Worker deploy atomically from one commit, so both always carry the same dataset bytes.
- Repo-verified, measured: the whole core public surface plus the dataset adds +4,874 bytes raw, +2,049 gzip (level 9), +2,050 gzip (default level, the one `bundle:check` uses) and +1,728 brotli (q11) to the web bundle (nearest, fare and dataset alone: +3,992 raw, +1,724 gzip level 9, +1,429 brotli). With the whole core in, `bundle:check` reports 230,751 raw and 72,471 gzip (default level) against the 250,000 and 80,000 budget, leaving 7,529 gzip bytes.
- Web-verified 2026-11-06: Workers Free allows 100,000 requests per day; static asset requests are free; requests matching `run_worker_first` (here `/api/*` and `/assets/*`) are billed Worker requests. Real traffic is Unknown, so no option is rejected on request counts (see the evidence model).
- Web-verified 2026-11-06: Google says browser keys use HTTP-referrer restrictions and server keys IP restrictions. That the Worker has no stable egress address is Inferred, not Web-verified (carried from ADR-0009). Whether `Route.computeRoutes` accepts a referrer-restricted key is Unverified.
- Web-verified 2026-11-06: a service worker can precache the app shell, with an update and versioning problem (`skipWaiting` can serve old pages with a new worker). No service worker ships today, so offline is only a possibility that this decision keeps open.
- Owner answers (2026-11-05, [nearest-station](../specifications/nearest-station.md) H1 to H3, [glossary](../product/glossary.md)): fares are Government fares, effective since launch (publisher not named); English only for now; the UI must not allow the same station at both ends. The Government notice is in [dhaka-mrt-line-6](../evidence/dhaka-mrt-line-6.md).
- The foundation blueprint (section 7.2) is a file outside the repository (a download); it is not a source here and its content is Unverified. The question was reopened by the ADR-0009 conflict above, and the options are judged on repository evidence.

### Options

- **A: all computation in the API Worker** (status quo layering). Strongest honest case: one copy of the data and the rules, no layering change, no dependency edit, ADR-0003 holds literally, a fare table changing on a date changes for everyone at the instant of deployment (no stale tab shows the old fare once it calls the API), requests can be logged for analytics, and a future paid or ticketing flow already has its server authority. Requests are not the problem it is sometimes made out to be: one bulk call for the station list and cacheable GETs for fares keep it to about 2 asset requests plus a few calls per session. Weakness: the rider's position must reach our server for nearest (the ADR-0009 consent copy would have to change), every lookup needs the network and a loading and failure state, and a Worker route plus contract exists for work a phone computes in microseconds.
- **A-prime: nearest station in the browser (what ADR-0009 requires), fare lookup and everything else through the API.** Strongest honest case: the position never leaves the device, and the fare, the one legally authored number, still has a server authority; a Government table that changes on a date for everyone at once changes at the deployment instant; a long-lived tab or a stale service worker cannot keep showing an old fare because the number is fetched; fare queries can be counted; a future ticketing flow needs no change of authority; the fare matrix (about 1 KB) leaves the bundle. Weaknesses: it needs the same layering change as B (web must run core for nearest), so it does not reduce layering work; it adds a contract, a Hono route, the ADR-0013 envelope path and a loading and error state for the fare page; the fare page needs the network (and dies with the Worker at its limit); and one dataset is split across two paths, so a stale tab can hold a station id the server no longer knows (an explicit `unknown-fare`, never zero).
- **B: core also runs in the browser; the API keeps what needs a server.** Nearest, search and fare in the browser from the dataset in the bundle; the API for the envelope, headers, observability and any future keyed or authoritative feature.
- **C: both; the API is the validating authority, the browser the fast path.** Strongest honest case: it combines B's speed with a server check. The check is not nearest-only: the server can validate a fare from two station ids with no position at all, and the check is deterministic (`findFare` is integer table indexing, so there is no floating-point drift). The weakness is purpose: the browser and the Worker run the same bytes of the same function, so the check can differ only under version skew, and then it only says "the newer deployment wins", which is A-prime's behaviour for fares at the price of a second request, a disagreement state and a second test surface.

## Decision

We will run `@metro/core` in the browser for station search, the nearest-station rule and fare lookup (option B), and will not add API routes that repeat those computations. This is accepted by delegation: the owner asked the agent to take the best decisions on 2026-11-06.

- The dataset ships inside the web bundle as part of core, reached through core's public entry only. `apps/api` keeps what needs a server (the error envelope and security headers, observability, and any later feature that needs a secret, shared state or an authority we do not have) and stays free to import core.
- Layering: only the rule changes. `web-never-imports-core-runtime` and its comment are replaced by `web-imports-core-public-entry-only` (exact edit under "Repository changes"). ADR-0003 is not edited and contains no sentence to amend. What stays true from ADR-0003: contracts govern everything that crosses the wire; web imports no API code; the page validates every API response with Valibot. Reversing the rule for pure local computation is acceptable now because there is no wire boundary and nothing to validate: a function call on the dataset in the same bundle cannot return a hostile or malformed body, and the code and the data are the same bytes the page was built from.
- Maps, Places and Routes stay in the browser with the referrer-restricted keys of ADR-0009. If Routes rejects a browser key or abuse appears, ADR-0009's Worker-proxy trigger adds an API route; the domain stays where it is.
- Authority. The authority behind the fares is the Government notice, not the client or the server; the dataset in the deployed bundle is the app's single versioned copy of it. A client never asks the server to confirm a fare today. The page shows fixed copy "Fares as of <dataset date>" (English only), using a dataset date field added by follow-up 2.
- Offline is deferred. This decision does not deliver offline and does not rely on it: no service worker ships, and the decision is justified without it (below). It only avoids closing the door.
- The fare publisher, notice reference and effective date (R7) remain an open fact the owner must supply; until then the dataset fields for them are optional and show as unknown.

### Reasoning

Why B beats A: A needs the rider's position on our server for the first slice, which contradicts the accepted ADR-0009 consent copy and would amend it; it adds a network round trip and failure state to a lookup the phone does instantly; and it keeps the repository's own decisions in conflict. A's remaining advantage (no layering change) is a one-rule edit.

Why B beats A-prime on the evidence, stated as the real argument. A-prime's strongest case is a server authority for fares: instant change for all on a date, no stale tab, fare analytics, a ticketing path. The evidence says those benefits are conditional or small today: (1) the same layering change is needed, so it saves none; (2) no fare revision since the 8 September 2022 notice was found (evidence file; Unverified as a negative), so "a table changing on a date for everyone" has not been seen in four years, and in B a deploy changes it for every new page load at the same moment, with open tabs stale only until reload; (3) no service worker ships, so the stale-service-worker case does not exist yet and, when a service worker is added, its update prompt and the visible dataset date are the control; (4) there is no payment or ticketing, which is the case where server authority matters and which is a named revisit trigger; (5) A-prime pays a contract, a route, an envelope path, a loading and error state and a network dependency for a 256-number table of about 1 KB, and splits one dataset into two paths with skew between them. B keeps one path and is the cheaper starting point, and moving B to A-prime later is a bounded change (a route, a contract and a call). The recommendation therefore stays B; A-prime wins if a revisit trigger fires.

Why B beats C: C's fare validation is real and deterministic, not nearest-only. It is rejected for now because it has no consumer: a check against the same bytes can differ only under version skew, nothing downstream (no payment, no dispute record) acts on the result, and it costs a request, a disagreement state and a second test surface per lookup. If ticketing or disputes appear, C or A-prime is the upgrade.

### Owner decisions (defaults delegated to the agent on 2026-11-06)

- Option B accepted (this ADR).
- Offline: not now. Revisit trigger: riders lose connectivity at stations or on trains and the owner wants the app to work there.
- Ticketing or payments later make the server the fare authority (A-prime or C). Revisit trigger.
- Fixed copy "Fares as of <dataset date>".
- Still the owner's to supply, because it is a fact not a choice: the fare publisher, notice reference and effective date (R7). Nothing in this ADR blocks on it.

## Consequences

- Easier: a nearest-station and fare result needs no network and no Worker request; the first reference slice has two layers (UI and core) and a golden path with no mandatory API step; the ADR-0009 consent copy stays true; Worker requests are spent only on assets and genuine server work; the decision is justified without offline, which stays possible.
- Harder: a fare correction needs a deploy and reaches an already open tab only on reload, so the dataset date must be visible and a stale-tab check is worth building (follow-up 5); the domain now runs in the browser engines riders use, so tests must prove it there; `apps/api` has little to do until a feature needs a server.
- Not changed: at the Workers Free daily limit a cold load fails in every option, because the hashed assets are `run_worker_first` Worker requests (1027 or 429, Unverified which). A page already loaded keeps working. B does not fix that; ADR-0011 owns that cost and its trigger.
- Risks: nobody can check a fare against a server (accepted; the version is visible); cross-engine floating-point differences in Haversine could change a near-tie in nearest selection (Unverified; follow-up 4 tests Chromium, Firefox and WebKit); a service worker, if added, needs an update and kill-switch plan (Unverified in practice).
- Revisit triggers (any one reopens this ADR through a new one): payments, ticketing or any decision a rider or operator must dispute against a server record; a second consumer of the domain (a native app, a third party, shared links) that cannot run core; the dataset grows enough that `bundle:check` headroom falls below 5,000 gzip bytes (default level; today 7,529 with core in) because of data, or the dataset alone exceeds 10 KB gzip; fares changing on dated schedules often enough that stale tabs matter; key abuse or Routes rejecting a browser key (then the proxy route appears; the domain stays); a measured disagreement of nearest selection between browsers; riders losing connectivity (offline spike).
- Reversibility: high (a wiring change) while no service worker exists; medium after, because a kill-switch worker is needed to remove one.

## Alternatives considered

- A, all computation in the API: rejected; reasons under "Why B beats A". It stays valid if a trigger fires.
- A-prime, nearest in the browser and fares through the API: rejected for now; reasons under "Why B beats A-prime". It is the first upgrade if ticketing, a fare-change cadence or a stale-tab problem materialises.
- C, both with the API as validating authority: rejected for now; reasons under "Why B beats C".
- B plus a service worker now: deferred; the offline value is not yet requested, and update behaviour, kill switch, Worker-first asset requests and plugin compatibility with the Cloudflare Vite plugin are unverified.
- Move Maps calls to a Worker proxy now: out of scope; ADR-0009 owns that decision and its trigger.

## Repository changes the recommendation requires (ticket drafts; not created in Plane)

Each is a bounded slice for a fresh session.

1. **Allow web to run core through its public entry.** Replace rule `web-never-imports-core-runtime` in `.dependency-cruiser.mts` with `web-imports-core-public-entry-only` (`from ^apps/web/`, `to ^packages/core/` with `pathNot ^packages/core/src/index\.ts$`, comment "The browser app may run core, but only through its public entry."); add `"@metro/core": "workspace:*"` to `apps/web/package.json` and update `bun.lock`; add the TypeScript reference in `apps/web/tsconfig.json` as `packages/contracts` has; replace the `scripts/layering.test.ts` cases (deep import rejected, public-entry runtime and type-only imports allowed, other rules unchanged and red on their fixtures); update the sentence in `docs/agents/architecture.md`; run `imports:check`, `unused` and `bundle:check`. Acceptance fails on base (a web runtime import is rejected there). No UI change; ADR-0003 is not edited.
2. **Dataset date and provenance.** Extend `StationDataset` and `validateDataset` with a required `asOf` date (the date the data was last checked against the source; the evidence records 2026-11-05) and optional `publisher`, `noticeReference` and `effectiveDate` (owner supplies; unknown stays explicit), with failing validation tests first.
3. **Reference slice "nearest station" in the browser.** Specification first, then a web feature that takes an injected or device position, runs `findNearestStation`, and shows the station, geographic distance and the fare to a chosen second station (same station excluded), with the fixed copy "Fares as of <dataset date>"; loading, empty, invalid-coordinate and recovery states; Vitest web tests with real core and injected positions; one Playwright journey with axe and keyboard checks; the golden-path guide reflecting "UI, then core; API only if a server is needed". Geolocation consent copy and handling are implemented in the map slice (ADR-0009).
4. **Cross-engine determinism check.** A separate test: all 16 stations and a grid of synthetic positions, including exact-tie and near-tie cases, produce the same nearest result in Chromium, Firefox and WebKit (the CI Playwright projects) as under Bun. If any differ, the ADR trigger applies.
5. **Stale-tab check.** Specification then implementation of a lightweight check that tells the rider when the page's dataset is older than the deployed one (for example re-fetching the HTML shell with `no-store` and comparing the hashed asset names on focus), without a new API route, with a visible refresh message.
6. **Offline spike (only when the owner wants offline).** Time-boxed prototype: precache the shell with `vite-plugin-pwa` 2.0.0 (peer `vite ^8` is Web-verified; compatibility with `@cloudflare/vite-plugin` 1.66.0 and `trustedDependencies: []` is Unverified), `registerType: "prompt"` rather than `autoUpdate`, `sw.js` at a stable root URL with the default revalidating `Cache-Control`, a kill-switch plan, and a count of asset requests through the `run_worker_first` Worker. Output is evidence plus an ADR.

If a trigger moves the decision to A-prime, A or C, follow-up 1 still applies to A-prime and C; for A the nearest-station slice instead needs a contract in `packages/contracts`, a Hono route with the ADR-0013 envelope, and a changed ADR-0009 consent copy.
