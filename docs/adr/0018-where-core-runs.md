# ADR-0018: Where the domain core runs

- Status: Proposed
- Date: 2026-11-06
- Ticket and specification: METRO-84 (Plane); no separate specification, the ticket acceptance is the contract. Evidence: [METRO-84 evidence](../evidence/metro-84.md). This is a proposal for the owner: nothing below is in force until the owner accepts it. (The number 0010 is unused in the repository history; this ADR takes the next free number, 0018.)

## Context

Today `apps/web` may import only types from `@metro/core` (dependency-cruiser rule `web-never-imports-core-runtime`), so every station, nearest and fare computation would have to go through `apps/api`. Meanwhile [ADR-0009](0009-maps-provider-design.md) already assumes the opposite for the first map slice: "the nearest station is chosen in the browser from our own dataset", the position "is not sent to our server", and fares and station lists "work with no map script loaded". The two accepted decisions cannot both hold for the nearest-station slice, and the first reference slice decides what every later slice copies. The foundation blueprint (section 7.2) suggests running core in the browser; that is an opinion, used here as a lead and tested against evidence, not a decision.

Facts, with labels and sources in the [evidence](../evidence/metro-84.md):

- Repo-verified: core is pure, dependency-free and tiny (16 stations, 16x16 fares, `baseline-v2`); the API has one scaffold route and does not use core for anything else; the SPA and the Worker deploy atomically from one commit, so both always carry the same dataset bytes.
- Repo-verified, measured: adding the whole core public surface and the dataset to the web bundle costs +4,874 bytes raw, +2,049 gzip, +1,728 brotli (nearest, fare and dataset alone: +3,992 / +1,724 / +1,429). The bundle becomes 230,751 raw and 72,471 gzip (`bundle:check` method) against the 250,000 / 80,000 budget; 7,529 gzip bytes stay free.
- Web-verified 2026-11-06: Workers Free allows 100,000 requests per day; static asset requests are free; requests matching `run_worker_first` (here `/api/*` and `/assets/*`) are billed Worker requests. A cold page load already costs 2 asset requests plus every API call.
- Web-verified 2026-11-06: Google says browser keys use HTTP-referrer restrictions and server keys IP restrictions; a Worker has no stable egress address (Inferred), so a proxied key cannot be IP-restricted. Whether the JavaScript `Route.computeRoutes` call accepts a referrer-restricted key is Unverified (ADR-0009 carried this forward).
- Web-verified 2026-11-06: a service worker can precache the app shell for offline use, but caching is the only way to make option A work offline and it brings an update and versioning problem (`skipWaiting` can serve old pages with a new worker).
- Owner answers (2026-11-05, [nearest-station](../specifications/nearest-station.md) H1 to H3, [glossary](../product/glossary.md)): fares come from the Government, effective since launch; English only for now; the UI must not allow the same station at both ends.

## Decision

This is the recommendation put to the owner. We will, once the owner accepts this ADR:

- Run `@metro/core` in the browser for station search, the nearest-station rule and fare lookup (option B). The dataset ships inside the web bundle as part of core, reached through core's public entry only.
- Not build API routes that repeat those computations. `apps/api` keeps what needs a server: the error envelope and security headers it already provides, observability, and any future feature that needs a secret, shared state or authority we do not have today. The API stays free to import core (it does today).
- Keep Google Maps, Places and Routes in the browser with the referrer-restricted keys of [ADR-0009](0009-maps-provider-design.md). This ADR does not change that; the ADR-0009 revisit trigger (a Worker proxy if Routes rejects a browser key or abuse appears) still governs, and a proxy would add an API route without moving the domain.
- Treat the dataset in the deployed bundle as the app's single authoritative copy of the Government fare table and station list, and show its `version` to the rider. The authority behind that copy is the Government notice recorded in [dhaka-mrt-line-6](../evidence/dhaka-mrt-line-6.md), not the client or the server. When a client and a newer deployment differ, the newer dataset version is right; a client never asks the server to confirm a fare.
- Change the layering by the exact edit in "Repository changes" below, and amend the web-layering sentence of ADR-0003 ("the web app gets runtime values through contracts") by this ADR: it was the reason for the old rule; contracts stay the only way for web to receive data from the API. Core stays dependency-free and unchanged.
- Not add a service worker in this decision. Offline use is made possible by this decision but is a separate owner decision (see below), because it brings update, kill-switch and Worker-first-asset questions that are unverified here.

### Reasoning

The decisive evidence is: the code costs about 5 KB; the dataset is public Government data with no secret; the app and the API deploy as one unit, so a server copy adds no authority (same bytes); a server-validating design (C) cannot validate "nearest" without receiving the rider's position, which the accepted consent text in ADR-0009 promises not to do; A needs the position on our server for the very first slice; and B removes the per-lookup Worker request while keeping offline possible. Option B is also the only one consistent with ADR-0009 without amending it. C is rejected because it is B plus work: nothing a server can validate here is not already the same function over the same bytes. A is rejected because it needs network for answers a phone can compute, spends the free-tier budget on that work, and contradicts ADR-0009.

### What is the owner's call

- Accept or reject B (the recommendation), or choose A or C.
- Whether the product must work offline, and therefore whether to open the service worker spike (follow-up 4); this is a product decision about riders on metro platforms and trains with weak signal, not a technical one.
- Fare authority policy if payments, ticket purchase or a published fare API ever appear: then the server may need to be the authority (revisit trigger).
- The publisher name, notice reference and effective date to record in the dataset (R7 is still open; the owner said fares are Government-set since launch but did not name the publisher).
- Whether showing the dataset version to riders is acceptable copy (English only for now).

## Consequences

- Easier: a nearest-station and fare result needs no network and no Worker request; the first reference slice has two layers (UI and core) and a golden path with no mandatory API step; offline becomes possible; the consent copy in ADR-0009 stays true; the Workers free-tier budget is spent only on asset requests and genuine server work.
- Harder: the dataset is public code in the bundle (it was always public data); a fare correction needs a deploy and reaches open tabs only on reload (or on the service worker update flow if one is added); the domain now runs in browser engines, so tests must prove it there; `apps/api` has little to do until a feature needs a server, so ADR-0013's envelope work stays with its few routes.
- Must be done with the decision: the layering edit and its red/green fixtures, the dependency and tsconfig wiring, docs that state the old rule (`docs/agents/architecture.md`), and the dataset provenance fields. See "Repository changes".
- Risks: nobody can check a fare against a server (accepted: a stale tab shows an old version, which the visible version number makes diagnosable); cross-engine floating-point differences in Haversine could change a near-tie in nearest selection (Unverified; mitigated by a tie test in the browsers that ship); once a service worker is installed on devices, removing it needs a self-unregistering worker (Unverified in practice).
- Revisit triggers (any one reopens this ADR through a new one): a second consumer of the domain (a native app, a third-party API user, a shared link service) that cannot run core; payments or ticketing, or any decision a rider or operator must be able to dispute against a server record; the web bundle gaining a dataset large enough to take the headroom below 20% of either budget (today 7,529 of 80,000 gzip bytes after core); the dataset changing faster than the deploy cadence; evidence of key abuse, or Routes rejecting a browser key (then the Worker proxy of ADR-0009 appears, and the proxy route needs authentication and rate limiting); a measured disagreement of nearest selection between browsers.
- Reversibility: high before a service worker exists (a wiring change); medium after (a kill-switch worker is required).

## Alternatives considered

- A, all computation in the API Worker (status quo): rejected. Offline is impossible; every lookup is a Worker request (about 14,000 cold sessions per day against the free limit, inferred); the rider's position would have to go to our server, which ADR-0009 promises it does not; and it keeps ADR-0003 and ADR-0009 in conflict. It stays the right choice if a trigger above fires.
- C, both with the API as validating authority: rejected for now. The browser and Worker run the same bytes, so validation adds a second code path, a disagreement rule, a UI state and cross-engine agreement tests without new authority; nearest cannot be validated without the position. It is the cheap upgrade from B (add a route and a contract) if payments or a second consumer appear.
- B plus a service worker now: deferred, not rejected. The offline value is real but update behaviour (`skipWaiting` mixed versions), kill switch, `run_worker_first` asset requests and plugin compatibility with the Cloudflare Vite plugin are unverified.
- Move Maps calls to a Worker proxy now: out of scope; ADR-0009 owns that decision and its trigger.

## Repository changes the recommendation would require (ticket drafts; not created in Plane)

Each is a bounded slice for a fresh session. All wait for the owner to accept this ADR.

1. **Allow web to run core through its public entry.** Replace rule `web-never-imports-core-runtime` in `.dependency-cruiser.mts` with `web-imports-core-public-entry-only` (`from ^apps/web/`, `to ^packages/core/` with `pathNot ^packages/core/src/index\.ts$`); add `"@metro/core": "workspace:*"` to `apps/web/package.json` (update `bun.lock`) and the TypeScript reference in `apps/web/tsconfig.json`; replace the `scripts/layering.test.ts` cases (deep import rejected, public-entry runtime and type-only imports allowed, all other rules unchanged and still red on their fixtures); update the sentence in `docs/agents/architecture.md`; run `imports:check`, `unused` (knip), `bundle:check`. Acceptance fails on base (the rule rejects a web runtime import). No UI change.
2. **Dataset provenance and version.** Extend `StationDataset` and `validateDataset` with `publisher`, `noticeReference` and `effectiveDate` (owner supplies the values; unknown stays explicitly `unknown`), expose the version for display, and add the failing validation tests first. Needs an owner answer on the publisher (R7).
3. **Reference slice "nearest station" in the browser.** Spec first (docs/specifications), then a web feature that takes an injected or device position, runs `findNearestStation` over the baseline dataset and shows the station, geographic distance and fare to a chosen second station (same station excluded), with loading, empty, invalid-coordinate and recovery states; Vitest web tests with real core and injected positions; one Playwright journey with axe and keyboard checks in Chromium and WebKit, including a tie case; the golden-path guide reflecting "UI, then core, API only if a server is needed". The ADR-0009 consent copy and geolocation handling are implemented in the map slice, not here.
4. **Offline spike (only if the owner wants offline).** Time-boxed prototype under `mattpocock-skills:prototype` rules: precache the shell with `vite-plugin-pwa` 2.0.0 (peer `vite ^8` is Web-verified; compatibility with `@cloudflare/vite-plugin` 1.66.0 and `trustedDependencies: []` is Unverified), `registerType: "prompt"` rather than `autoUpdate` (which forces `skipWaiting` and `clientsClaim`), `sw.js` at a stable root URL with the default revalidating `Cache-Control`, a visible update prompt and dataset version, a kill-switch plan, and a measurement of asset requests through the `run_worker_first` Worker. Output is evidence plus an ADR, not a feature.
5. **Cross-engine tie determinism check.** Folded into follow-up 3 as an acceptance case: all 16 stations and a grid of synthetic positions, same result in Chromium and WebKit as in Bun; if any differ, this ADR's revisit trigger applies.

If the owner chooses A or C instead, follow-up 1 is not made, and the nearest-station slice instead needs a contract in `packages/contracts`, a Hono route in `apps/api` with the ADR-0013 envelope, and the ADR-0009 consent copy changed to say the position is sent to our server.
