## Held back, and why

- The share image (`og-default.png`). The handoff's file is not in the repository (METRO-107 did not copy it), so there is no master. Drawing one with this repository's script would put text in a PNG, and the drift check compares decoded pixels with a tolerance of 1: text rendering differs between Windows and the hosted Linux runner, so the check would fail there (Unverified, not run on Linux). It also needs the production origin: `og:image` must be an absolute URL and the custom domain is not set. Needed from the owner: an SVG master with outlined text, and the origin. A test still fails if any `og/` file appears in `public/`.
- The install screenshots. Not restored. They have to be generated from the real UI by Playwright, the same text-rendering drift applies to any check on them, and they would join the precache unless excluded. Left for a follow-up ticket; `manifestProblems` still rejects a `screenshots` member.

## Findings worth the owner's attention

- Playwright routes and the worker (Repo-verified): with a worker controlling the page, WebKit let the real Maps script and its follow-up requests through to `maps.googleapis.com` instead of the route stub. Two of my runs did this before I removed the test step that asked for Google (a focus on the place search): the key sent was the fake `fake-key-for-tests`, nothing was read or kept. No other spec allows the worker, `serviceWorkers: "block"` is the project default, the specs that allow it mark their pages (`workerMayControl`, after which the place-search helpers throw), and `e2e/offline-shell.e2e.ts` fails any test in which a request leaves `127.0.0.1`. This is stated plainly because the rule is that no automated run reaches Google.
- Firefox: `context.setOffline(true)` fails navigations with `NS_ERROR_OFFLINE` before the worker can answer, so the real-server tests that use it skip Firefox with that reason on the test; the static-server group covers Firefox by closing the server's connections. Firefox also does not report the worker script request to Playwright, so the "worker request comes after load" half is Chromium and WebKit; the "registration chunk is not fetched before load" half runs in all four.
- `fetch("/favicon.ico")` from a page fails under Playwright Chromium. Cause narrowed (Repo-verified): it fails the same way against a plain Node server that answers every path with 200 (`/favicon.ico` throws, `/favicon.ico?x=1`, `/other.ico` and `/x.png` succeed), no `requestfailed` event fires, and a Node-side request for the file gets 200 `image/vnd.microsoft.icon` from the real Worker. So the Worker route, `_headers`, the CSP, `nosniff` and the content type are not the cause; it is the browser or Playwright treating that one path specially (the exact mechanism is Unverified, and whether real Chrome does the same is Unverified). The file is not precached; the page also declares `favicon.svg` and `apple-touch-icon.png`.
- The captured `installing` worker reference did not deliver the skip-waiting message in WebKit; the registration's waiting worker did. The code tells the registration's waiting worker.
- Defects the browser runs found that the unit tests had missed (all fixed, all now tested): the worker passed `scope.fetch` detached ("Illegal invocation", every install failed until fixed); WebKit reported the first install as "installed" after the page was claimed, which showed an update prompt on a first visit ("update" is now decided from `registration.active` when the worker is found); the update e2e "cannot install" first passed vacuously (it now records the states from the page and requires `redundant`, never `installed`); and the kill-switch worker as first written reloaded open pages, which would loop for as long as the kill build is deployed because every page registers `/sw.js` after load (it no longer reloads pages).
- A Chromium takeover race found by stress runs (12 workers, repeated): about one Reload press in four did not take over, the old worker having been restarted while it was being stopped; with the page settled and a 3 s reading pause before the press, about 1 in 100 per run (4 of 408 runs of the whole spec); a second takeover in one page failed far more often than the first, so a multi-deploy e2e was tried, then a single takeover with a seeded older cache, and both were removed (the unit tests cover the deletion). Also tried and removed: stopping the idle workers first, removing the tool's request interception, and an automatic fallback reload after 5 s (the navigation hung too). The cause is Unverified and points at the test tool's debugger attach to a restarted worker; the product shows the fixed failure words and stays usable. It is the likeliest reason for a red hosted run of `offline-shell.e2e.ts` (Reload tests, Chromium and Pixel 7); if it recurs, serialise the update-flow group. Also found: `context.setOffline` hangs on a stopped worker, so the phone's normal case (worker stopped by the browser, then offline) has no automated test and is owner phone check 1.
- Under the combined four-browser run on a loaded machine, Firefox crashed its compositor (`RenderCompositorSWGL`) and timed out in axe teardown; the same specs pass when Firefox runs alone. The pre-push hook (check plus Chromium smoke) failed four times on 30 s timeouts of existing heavy specs, a slow lab LCP and once on an order- and timing-dependent METRO-113 test (`denied with Maps unavailable has no action`, passes 10 of 10 alone) while other sessions loaded the machine, and passed on a later attempt. A flaky test is a defect: if it recurs on the hosted run, serialise the update-flow group.
