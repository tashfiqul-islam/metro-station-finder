Locked tool installs and hook visibility (METRO-45). `mise.lock` (tracked, with the `.mise/locks/` dependency-graph sidecar) records per-platform URL and sha256 for every tool in `mise.toml`, for `windows-x64` and `linux-x64` only (`settings.lockfile_platforms`; macOS is not supported and would need `mise lock --platform` plus a reviewed entry). `mise install --locked` resolves tools only from the lock and fails on a checksum mismatch or a tool missing from the lock; verified 2026-11-05 on this machine by corrupting a recorded pkl checksum (install failed with "Checksum mismatch") and by removing the pkl entry ("not in the lockfile"). The lock verifies downloads, not files already installed or restored from a cache. What "locked" means where: CI installs are locked because every workflow that uses `jdx/mise-action` sets workflow-level `MISE_LOCKED: "1"` (a test globs `.github/workflows/*.yml` and fails if one lacks it); the action also adds `--locked` itself when `mise.lock` exists (mise-action README, Web-verified 2026-11-05), so the env is explicit belt and braces. Local installs are locked only if the developer runs `mise install --locked` as documented. `bootstrap` never runs mise: it does not install or verify tools, it validates that `mise.toml` and `mise.lock` agree (and that the running Bun and Node match the pins). mise has no read-only "verify the lock" command (`mise ls` has no `--locked`; `mise install --dry-run` does not download), so no stronger local check is claimed. `mise.toml` deliberately does not set `locked = true`: that would also lock personal global tools (for example `latest` entries) on a maintainer machine, so a personal global config that pins `latest` must be bypassed locally with `MISE_GLOBAL_CONFIG_FILE` pointing at an empty file. Trust anchors differ per tool: `gitleaks` and `pkl` checksums come from mise's metadata service (`checksum_source = "mise-versions"`, from the release asset digests GitHub reports), `actionlint` and `zizmor` also carry `provenance = "github-attestations"`, `hk` records a sigstore signer (`sigstore-oidc` workflow identity), and `bun` and `node` record the checksums published with their releases; none of these is an independently signed statement for every tool. `hk` locks as `backend = "packslip:github.com/jdx/hk"` because that is what mise 2026.10.25, the version every workflow pins, resolves for the short name `hk` (Repo-verified: the lock was generated with that exact version); a different mise could resolve another backend, which `scripts/mise-lock.ts` would then report. `npm:renovate` records its resolved dependency graph (`aube` digest plus the tracked sidecar) and its `trust_policy_excludes` option, so the owner-approved `@yarnpkg/libzip@3.2.2` exception is part of the lock. Update a pin by editing `mise.toml`, running `mise lock` (never edit `mise.lock` by hand), reviewing `git diff mise.lock .mise` and committing both; `scripts/configuration.ts` (part of `check` and `bootstrap`) calls `scripts/mise-lock.ts`, which fails when the lock and `mise.toml` disagree on the set of tools, version, specifier, reviewed backend (a table in the script; add a new tool there in the same change), `trust_policy_excludes`, or when a platform entry lacks a sha256 checksum or an https `github.com`/`nodejs.org` URL containing the pinned version. For npm tools it checks that `aube.path` stays under `.mise/locks/` and that `aube.digest` equals the sha256 of the tracked `aube-lock.yaml` (reproduced against mise 2026.10.25). It does not re-download anything, so it cannot tell whether a recorded checksum matches the real artifact; mise does that at install time. `/mise.lock` and `/.mise/` are in CODEOWNERS. Renovate documents `mise.lock` updates and `lockFileMaintenance` (`mise lock --bump`) for the mise manager, which needs `mise` in self-hosted `allowedUnsafeExecutions`; whether the hosted Renovate used here runs it is Unverified. If it does not, a Renovate pin bump fails `check` visibly until `mise lock` is run on the PR branch. Sources (Web-verified 2026-11-05): https://mise.jdx.dev/dev-tools/mise-lock.html, https://mise.jdx.dev/configuration/settings.html, https://github.com/jdx/mise-action, https://docs.renovatebot.com/modules/manager/mise/. Lock generation was run on Windows only; the linux-x64 entries were resolved by `mise lock` from release metadata and attestations, and the first ubuntu-24.04 CI run is the real check (Unverified until then).

`bootstrap` also warns, without failing, when `pre-commit`, `commit-msg` or `pre-push` hk hooks are not configured in Git (`git config --get-regexp '^hook\.hk-.*\.event$'`, which sees per-repo and global installs) and prints `mise exec -- hk install --mise`. It warns instead of failing because a fresh CI checkout never has hooks and CI is the backstop; it is skipped when `CI=true` and outside a Git checkout. If Git cannot be run it prints a "could not determine" warning with the same command instead of crashing. The required hook names are tied to `hk.pkl` by a test. On Git older than 2.54 hk writes script shims, which this check does not see, so it warns anyway; upgrade Git. hk 2.11.0 has no status command (Repo-verified via `hk --help`).

#### Cloudflare preview (METRO-13)

Same-repository pull requests opened by a person (never a bot, see METRO-47 below) get a Worker `metro-scaffold-pr-<number>` on workers.dev, deployed by the `preview` job of `.github/workflows/quality.yml` after `checks`, `build` and `security` pass (skipped for documentation-only pull requests, see [quality gates](../agents/quality-gates.md)); `preview-cleanup.yml` deletes it when the pull request closes. The job is outside the `Quality gates` aggregate. `CLOUDFLARE_API_TOKEN` (secret) and `CLOUDFLARE_ACCOUNT_ID` (variable) live only in the GitHub environment `preview`; a missing one fails the job with a message naming it. The token needs Workers Scripts edit for this account only; the owner rotates it (the first expiry, 2026-12-03, was extended by the owner to 2027-11-04; see the METRO-33 section of the [maintenance runbook](../agents/maintenance-runbook.md)). Rollback: `wrangler rollback --name metro-scaffold-pr-<number>` returns the preview to its previous version (the job exercises it, then redeploys the checked commit). Never run these against `metro-scaffold` (production). Decisions: [specification](../specifications/cloudflare-preview.md), [ADR-0006](../adr/0006-cloudflare-preview.md).

#### Credentialed CI jobs (METRO-47)

A job that holds `CLOUDFLARE_*` or `PLANE_*` values must not run code that came from a restored cache or from an unreviewed bot bump. `bunx wrangler` executes `node_modules` code with the token in its environment, and mise-action warns against restoring caches in credentialed jobs (Web-verified 2026-11-05: <https://github.com/jdx/mise-action>).

- **No restored caches (what is enforced).** A job is credentialed when it, or its workflow, mentions a `CLOUDFLARE_` or `PLANE_` name, reads the `secrets` context in any expression (`secrets.X`, `toJSON(secrets)`), sets a GitHub `environment:` or `secrets:` (including `secrets: inherit`), or uses a local reusable workflow or composite action (`uses: ./...`); every job of a `workflow_call` workflow counts too. Workflow-level `env:` only counts when it holds one of those names or reads secrets. Such a job has no `actions/cache` step and sets `cache: false` on every `jdx/mise-action` step, including steps inside a local composite action (its `action.yml` is read; an unreadable one fails). Other cache mechanisms, for example a setup action's own `cache` input, are not detected; do not add one to a credentialed job. This covers the `preview` job, `preview-cleanup.yml`, `production-deploy.yml`, `release-sync.yml`, `release-draft.yml` and `cloudflare-token-check.yml`. Decision: uniformity beats speed, so the preview and cleanup jobs install dependencies cold (slower; the Bun install cache stays in the non-credentialed `Checks`, `Build and smoke` and `Security` jobs). `scripts/ci-hardening.test.ts` parses every file in `.github/workflows/`, so a new workflow is covered without a list, and fails on a violation. `MISE_LOCKED` and the pinned action SHAs are unchanged.
- **No bot gets the Cloudflare token.** The `preview` job and the cleanup job AND together, in their `if`: the same-repository check, `!endsWith(github.actor, '[bot]')`, `!endsWith(github.event.pull_request.user.login, '[bot]')`, `github.event.pull_request.user.type != 'Bot'` and `github.event.sender.type != 'Bot'` (the preview job also checks `github.event_name == 'pull_request'`). The test requires every term as a separate AND term and rejects any `||`, so a term cannot be bypassed. This replaces the Dependabot-only check: Renovate pull requests are same-repository, so they used to run the preview. The type checks cover bot accounts whose login has no `[bot]` suffix; the pull request payload's `user` and `sender` objects carry `type` (the webhook payload is the standard GitHub user object). Unverified: the current GitHub docs do not enumerate the `type` values or name the Copilot coding agent login, so that a Copilot-authored pull request is excluded relies on its account type being `Bot`; the suffix checks alone would miss a login such as `Copilot`. Bot pull requests (Renovate, Dependabot) still get `Checks`, `Build and smoke` and `Security`, just no Cloudflare preview and no preview Worker. The author check also covers a human pushing onto a bot branch, which the actor check alone would miss. Consequences: a bot that pushes or rebases onto a human's pull request (a Renovate rebase, an auto-fix commit) makes the `sender` a bot, so the preview is skipped for that run and the preview Worker is stale or never created until a human pushes again; this is accepted, consistent with excluding every bot. A human pull request closed by a bot leaves its preview Worker behind; delete it by hand with the commands in the Cloudflare preview section.
- **Token scope.** Use an account-owned API token limited to the one Metro account, and two tokens, one for `preview` and a different one for `production`, each stored only in its GitHub environment, each with an expiry and its own rotation date (the production token already rotates on its own schedule, see Production deploy). Web-verified 2026-11-05 against <https://developers.cloudflare.com/fundamentals/api/reference/template/>: the "Edit Cloudflare Workers" template is not Workers-edit-only; it grants Account: Workers Scripts Write, Workers KV Storage Write, Workers Tail Read, Workers R2 Storage Write and Account Settings Read; Zone: Workers Routes Write; User: User Details Read and User Memberships Read. Context7-verified against <https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/>: Cloudflare's CI guide starts from that template and says to scope the account and zone resources down as far as possible. Recommendation: do not keep the template as is; create a custom token with the narrowest set that makes the preview job pass, starting from Workers Scripts Write on the one account, and add a permission only when a job fails for lack of it (drop KV, R2, routes, zone and user permissions the previews do not use; add Account Settings Read or Workers Tail Read only if wrangler needs it). Context7-verified against <https://developers.cloudflare.com/workers/authorization/>: wrangler uses exactly the permissions of an account-owned token, a granular `Editor` role deploys an existing Worker, and creating a new Worker needs `Admin` at the Workers product scope. Unverified, owner check in the dashboard: which permissions the tokens stored in `preview` and `production` have today, whether they carry the template's KV, R2, routes and user permissions, and whether the legacy Workers Scripts group behaves like the granular roles when the preview creates a per-pull-request Worker; the first preview run with a narrowed token is the live check. Rotation steps and the expiry alarm: see the METRO-33 section below.
- **OIDC.** Watch only. Cloudflare has no first-party OIDC for wrangler (see the METRO-33 section of the [maintenance runbook](../agents/maintenance-runbook.md)); nothing changes until it does.

#### CI concurrency and timings (METRO-59)

`Quality` cancels a superseded run only for pull requests: `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. Its concurrency group is the pull request ref for pull requests and the commit SHA for pushes, so every integration-branch commit keeps its own verdict. Context7-verified 2026-11-05 against <https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency>: at most one run can be pending in a group and a newly queued run replaces and cancels the existing pending one, so a non-cancelling shared group would still lose commits; the same page documents `queue: max` as an alternative (not used). Deploy, release and token-check workflows keep `cancel-in-progress: false`, and so do the group of any credentialed job (the preview and cleanup jobs), which a test pins to exactly `false`. `Reviewer record` uses the same pull-request-only expression; it only triggers on `pull_request`, so the expression is always true there and behaves like `true`. It is written that way on purpose, so a single rule (absent, false or exactly this expression) governs every workflow and a new trigger added later cannot start cancelling unconditionally. `scripts/ci-hardening.test.ts` asserts from the parsed workflows that every `cancel-in-progress` is absent, false or exactly that expression, and that credentialed non-pull-request workflows never cancel. A pull request closed by a bot, or a cancelled superseded pull request run, is expected to show as cancelled; that is not a missing verdict. Measured job durations and the sharding decision: [CI timings](ci-timings-2026-11.md).

#### Release sync (METRO-14)

Publishing, editing, unpublishing or deleting a GitHub release runs `.github/workflows/release-sync.yml`, which keeps Plane aligned through `scripts/release-sync.ts`: the Plane release (looked up by tag name, never duplicated), its release tag (`git_tag`, `commit_hash`) and its release log (the GitHub notes rendered to HTML). GitHub is canonical. A stable release becomes `released` only when a successful `production` deployment exists for the tagged commit (none exists before METRO-11); a prerelease, draft or retracted release never does. Historical released Plane releases (`v0.0.1`, `v0.0.2`) are never modified. Publishing a release never changes work item states.

- **Run it by hand:** Actions, Release sync, Run workflow, tag `vX.Y.Z`. Use this after a failed run; the run is idempotent.
- **Credential:** `PLANE_API_KEY` is a secret in the GitHub environment `release`, which requires the owner's approval for every run and only accepts tags `v*` and the branches `main` and `feature/metro-rebuild`. The key acts as its owner in Plane and expires 2027-02-03; rotate it before then.
- **Release notes** list the METRO tickets and pull requests included and have a "Deferred" heading for unfinished tickets; the sync reports a missing heading in the Plane description.
- **Retraction:** delete or unpublish the GitHub release; the next run resets the Plane release to `unreleased`. Specification: [release-sync](../specifications/release-sync.md).
- **Not covered:** creating a GitHub release from Plane (separate ticket, needs a trigger that works before the default-branch switch).

#### Production deploy (METRO-57)

`.github/workflows/production-deploy.yml` deploys a stable `v*` tag (or `main` by dispatch) to the Worker `metro-scaffold` through the approval-gated `production` environment: upload a version, stage it at 0 percent, smoke it, roll it to 100 percent, smoke, soak, smoke, with automatic `wrangler rollback` on failure. It is off until the owner sets `PRODUCTION_DEPLOY_ENABLED=true`. Decisions: [ADR-0012](../adr/0012-production-deploy.md); owner setup, read-only checks and manual rollback: [deploy runbook](../agents/deploy-runbook.md). The production Cloudflare token is separate from the preview token; rotate it on its own schedule.
