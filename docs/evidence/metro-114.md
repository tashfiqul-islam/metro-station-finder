# METRO-114 evidence: Nearby 4/4, Google place search on first focus, the walking route and the Google JS map removal

Date: 2026-11-09. Base: `b048d78` (`feature/metro-rebuild`, merge of PR 115, the location flow). Head: the tip of `ticket/metro-114-google` in the pull request. Windows 11, Bun 1.4.4, Node 26.13.0, Playwright 1.64.1, `@googlemaps/js-api-loader` 2.1.3, `@types/google.maps` 3.66.9. Scope: the ticket (METRO-114) and the umbrella METRO-109. Labels: Repo-verified, Context7-verified, Web-verified, Unverified.

## What shipped

- `adapters/maps`: the provider loads nothing at mount. `MapsState` gained `load()` and the status `idle`; the Maps script (Places and Routes libraries, one request) loads when something calls `load()`: the first focus of the place search, or the first walking route. A 20 s watchdog gives up on a script that never answers; a load that failed while the browser reported no connection is retried when the `online` event fires (`resetLibraries`), a load that failed while it reported a connection is not (every attempt is another request to Google).
- `place-search.tsx`: a plain `<input>` named by the visible `<label>` and described by the visible hint. Its first focus calls `load()`. When the Places library is there, `PlaceAutocompleteElement` is created, the typed text goes into its `value`, the plain input is hidden (not removed, so text typed during the load is never lost) and focus moves to the widget only if the plain input still had it. `focus.ts` focuses the host and, when its shadow root can be read, the inner input with the caret at the end.
- `NearestStation.tsx`: with no connection (`navigator.onLine` false), no key or a failed load, the label, hint and field are replaced by one small warning notice (a `status` region mounted from the start and empty, so a later notice is announced). Focus that was in the field when it vanished moves to the notice. The "Search for a place" action in the location notices is left out in that state (METRO-113 follow-up) and focuses the field (the plain input, or the widget once swapped) otherwise. Typing in the search opens the sheet to full, like the station picker, so the suggestion list has room; focus alone does not (Tab through the page never moves the sheet).
- `walking-route.ts` / `LocationResult.tsx`: one `useWalkingRoute` call per mounted result, for a good device fix and for a chosen place. The result is mounted only for those two; a rough fix, a picked station and an invalid position never mount it. The first call also asks the provider to load. A 15 s watchdog ends a route that never answers as the fixed failure copy and ignores the late answer. Walk time and distance read "about 1.2 km, 15 min · est.".
- Nothing draws a Google map: the SVG line map was already the map (METRO-111). What left the first-visit path is the Maps script itself (it loaded at Nearby mount before).
- `smoke:live` and its runbook follow the new flow (see below). ADR-0009 and the slice specification carry a METRO-114 note.
- Tests: Vitest for the provider (idle, ask once, watchdog, retry on `online`), the loader reset, the place search swap (typed text, focus, caret, no focus steal), `focus.ts`, the walking route (one request, re-render, replaced result, watchdog), the availability states and the report lines of `smoke:live`; Playwright `e2e/place-search.e2e.ts` (new) and edits to the files listed below.

## Google, billing and the caps

- Session tokens (Context7-verified, 2026-11-09, Google's Place Autocomplete (New) and Autocomplete data pages): a session groups the typing and the selection; it ends when `fetchFields()` is called on the `Place`; with `PlaceAutocompleteElement` the first `fetchFields` on the `Place` from `PlacePrediction.toPlace()` includes the session token automatically. The element therefore starts a session with the user's typing and ends it at the selection; a new one begins with the next typing. This slice does what the ticket asks in effect (one search is one session) but not by creating a token: the app creates and passes none, because the element has no documented way to take one and a token the app made would not be the one it used. One selection calls `fetchFields` once, with `["location"]` only (Essentials). Unverified: how the console splits the billed SKUs (the owner-run live check and the console, as in the runbook).
- Caps unchanged and documented where they were: map loads 300, Autocomplete 100, Place Details 100, Routes 100 per day (`docs/agents/maps-live-check-runbook.md`, ADR-0009 amendments). The app adds no limiter of its own; the console quotas stay the enforcement. Request counts this slice adds per user action: first focus loads the script (one map-load-type request, no map drawn, Unverified whether billed), one route per good fix or chosen place. The route service still shares one request between identical pairs rounded to 4 decimals, so pressing Use my location again at the same spot asks for 0 more.
- The user's position goes to Google only to work out the route; nothing of it reaches our Worker (`e2e/place-search.e2e.ts` and `e2e/location.e2e.ts` check `/api` and every request recorded). The Directions link carries only the station's public coordinates.

## Decisions and deviations

- Swap without focus: when the libraries are already loaded (a good fix loaded them for its route), the widget replaces the plain input at once, with no focus move, because there is nothing left to wait for.
- No `offline` listener: the built-output test of METRO-112 forbids the word in any shipped script (until METRO-106), so the hook listens for `online` only and reads `navigator.onLine` at render. Going without a connection while the page is open is seen at the next render, and a failed load covers the rest. The no-connection copy therefore avoids the word and the handoff's "Stations and fares still work" (an offline-use claim). The provider's internal failure state is named `failed-no-connection` for the same reason.
- Sheet to full on typing in the search (the ticket describes "when the sheet snaps to full while typing" without saying what snaps it). Same rule as the station picker (`onEngage`); a result then settles it at half. It is the `input` event, not focus: an earlier draft used focus and a Tab walk then left the map controls behind a full sheet (the e2e keyboard test caught it on a phone-sized project).
- A device fix now shows its route, which the consent line ("Your position goes to Google only to work out the walking route") already said; METRO-113 flagged it as ahead of the code, it is now true.
- Searching for a place unmounts nothing but the location result: the one-current-result model of METRO-113 is unchanged (`Nearby` holds one value; a place is a `location` outcome with no pin).
- A load that hangs ends after 20 s and a route after 15 s (new constants `LOAD_WATCHDOG_MS`, `ROUTE_WATCHDOG_MS`); the first reads as "place search unavailable" for the rest of the page's life, as any failed load does.
- The fake widget in `e2e/maps-stub.ts` forwards `focus()` from its host to its input. That is the best case; whether Google's host does is Unverified (see below). It also draws a popup, so the list test proves our containers do not clip or cover a popup, not how Google draws its own.
- Existing e2e edits, with reasons: `nearest-station.e2e.ts` (the field starts plain, so searches go through `searchForPlace`; the walking text is now "about 1.2 km, 15 min · est."; the METRO-113 test that asserted no route for a device fix is replaced by one that asserts exactly one; the failure copy changed; the script-failure test is rewritten because the script no longer loads at page load; the keyboard test names the plain input; the ARIA snapshot has the label as text and the plain textbox; the stub-wiring test checks both phases; the styling count is unchanged at 2 linked sheets and 0 style attributes, which needed the stub's popup to use a constructable stylesheet, not a style attribute). `location.e2e.ts` (a good fix now shows its route; the denied search action ends with the widget focused and the sheet full; the no-request test allows the one Maps script request a fix now causes and expects one route; the keyboard-order test matches the search stop ignoring case because Tab through the plain input swaps the widget in). `headers.e2e.ts` (the fail-closed fixture test focuses the field, because nothing loads at page load any more). `error-fallback.e2e.ts` (searches through the helper). No assertion was removed or loosened to pass: each was changed to the new behaviour or replaced by a stricter one.

## Facts recorded after review

- StrictMode: production wraps the app in `<StrictMode>` (`apps/web/src/main.tsx`, Repo-verified), so every effect runs twice in development builds and, as React documents it, only there; the production build does not double-run effects. The route guard is kept for both: a result's request is made once and a later effect run for the same key attaches to it. The unit test mounts under `StrictMode` over the real `createRouteService` with a counted fake `Route.computeRoutes`, and counts `walk` calls as well: a good fix is 1 and 1, a place adds 1 and 1, a re-render and a theme change add 0. Mutation checks (each reverted afterwards, run in `NearestStation.test.tsx`): removing the per-key request guard fails the StrictMode test and the stored-failure test; removing the service's cache fails the "same fix twice" test (two results, two `walk` calls, one Google request); restoring the old blur rule fails the click-away focus test.
- A stored failure followed by a new `service` object does not ask again: the failure is stored by the watchdog, the service is replaced, the first service was called once and the second never (test).
- Where the Google code lands (build manifest, `bun run build`): `maps-*.js` (5,805 raw / 2,843 gzip, lazy) holds `provider`, `libraries`, `@googlemaps/js-api-loader`, `place-search` and the route service; the entry (`index-*.js`, 235,018 raw) contains none of `importLibrary`, `maps.googleapis.com/maps/api/js`, `PlaceAutocompleteElement` or `computeRoutes`, has no static import, and `index.html` has only `theme-boot.js` and the entry module script: no Google script, no preconnect, no dns-prefetch.
- CI never runs `smoke:live`: no file under `.github` mentions `smoke:live` or `smoke-live` (grep, empty), and `ciRefusal` in `scripts/smoke-live-report.ts` refuses to run when `CI` is set.
- Connection lost mid-session is noticed only at the next render (the hook listens for `online`, not for its opposite: the built-output test of METRO-112 forbids that word in shipped scripts). Declared, no code change.
- Residual: when `searchAvailable` flips to false (no key after a failed load, or a render that reads no connection) `PlaceSearch` unmounts and the widget is removed. A typing session the user had begun in Google's element is abandoned without a selection: its Autocomplete requests were billed, no Place Details call follows, and Google's session simply expires. Rare (it needs the flip to happen while the user is typing); recorded, not mitigated.
